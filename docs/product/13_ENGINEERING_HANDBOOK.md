# Engineering Handbook

This is the onboarding guide for any human or AI agent joining AutoIngest engineering. It answers *why* the system is shaped the way it is — the authoritative *what* remains the technical docs under `docs/` (see `docs/CLAUDE.md`) and, for current behavior specifically, `docs/system-contracts.md`. This handbook is downstream of those, not a replacement for them: every claim below is derived from an existing project document or decision, cited inline. Where the repository has no documented stance, this says so rather than inventing one.

If you read nothing else before writing code or documentation here: read [system-contracts.md](../system-contracts.md) (the non-negotiable invariants), [05_DOCUMENTATION_WORKFLOW.md](05_DOCUMENTATION_WORKFLOW.md) (how to keep this system alive), and [CLAUDE.md](CLAUDE.md) (the AI operating manual for this directory).

## 1. Application Philosophy

AutoIngest is a structured-archival ingestion tool, not general-purpose photo management (`docs/product/00_PROJECT_VISION.md`). Every import is driven by an explicit event definition; every output path is deterministic; every file operation is designed to be safe to re-run. The core architectural stance, unchanged since foundation: `event.json` is the single source of truth, the UI is a pure reflection layer, and ingestion is transactional (`docs/CLAUDE.md` § Core Architecture, § Transactional Ingest Layer). These are not aspirations — they are enforced contracts (`docs/system-contracts.md`), and a violation is treated as a defect requiring redesign, not a style preference (`docs/decision-matrix.md` § 8).

## 2. Digital Archival Philosophy

AutoIngest automates and standardizes an archival workflow that predates it — it did not invent Aljamea-tus-Saifiyah's foldering or metadata conventions ([DEC-004](decisions/DEC-004_PRESERVE_BRIDGE_BASED_ARCHIVAL_PRACTICE.md), `11_ARCHITECTURAL_EVOLUTION.md` §3A). Adobe Bridge and professional human review remain part of the real workflow, not legacy artifacts being phased out (`11_ARCHITECTURAL_EVOLUTION.md` §3C, §3H) — AutoIngest automates *around* that review, not *away* from it. The archive is local-first and on-premises by design ([DEC-003](decisions/DEC-003_LOCAL_FIRST_ON_PREMISES_ARCHITECTURE.md)): sensitive institutional media stays under the institution's own storage control, with no required cloud dependency.

## 3. Metadata Philosophy

Metadata is a first-class, durable archival property of every eligible file, not an optional enhancement (`docs/product/00_PROJECT_VISION.md` § Role of metadata). Import always precedes metadata — a copy failure never blocks metadata, and a metadata failure never blocks or rolls back a copy (`docs/metadata-system.md` § Purpose). Every workflow (Standard Import, QMZ, Reapply, crash-recovery resume, Repair) consumes the same shared resolver and write engine ([DEC-007](decisions/DEC-007_SHARED_METADATA_ENGINE_RESOLVER.md)) — this was not the original design; it was adopted after an independent-context-construction pattern caused a real, silent metadata-loss defect ([BUG-007](bugs/BUG-007_QMZ_METADATA_CONTEXT_SHAPE_MISMATCH.md), [PM-001](postmortems/PM-001_METADATA_CORRECTNESS_GAP_PRODUCTION_READINESS_REVIEW.md)). A write is never trusted because the write call succeeded — the engine's shape is always `Expected → Write → Read Back → Compare → Result` (`docs/metadata-system.md` § The Shared Write Engine). Metadata never touches capture-date fields, by construction, not by convention (`docs/metadata-system.md`: "Explicitly never written by any AutoIngest metadata path").

## 4. Folder Hierarchy Philosophy

Folder structure and embedded metadata are complementary, and neither replaces the other ([DEC-002](decisions/DEC-002_FOLDER_STRUCTURE_PLUS_EMBEDDED_METADATA.md)). The Collection → Event → SubEvent → Photographer → media hierarchy (`docs/event-system.md`) is a deliberate, human-legible encoding of the same archival context also written into metadata — not an arbitrary storage detail (`11_ARCHITECTURAL_EVOLUTION.md` § 2). Path generation must be deterministic from `event.json` alone; no dynamic path computation happens during import, and folder names are never recomputed at import time (`docs/event-system.md` § Routing Relationship, § Rules).

## 5. Naming Philosophy

Collection naming follows `{HijriDate}_{Label}`; event names are deterministically generated from components and must remain stable once created (`docs/event-system.md` § Naming). Photographer folders use a `PCxx-` sequence prefix convention, resolved against existing on-disk sequenced folders before a new plain-name folder is ever created — a fallback that skips this check produces duplicates ([BUG-002](bugs/BUG-002_PHOTOGRAPHER_SEQUENCE_FOLDER_RESOLUTION.md)). Metadata keywords are never derived from collection name, full event folder name, photographer name, or QMZ sequence code (`docs/metadata-system.md` § Keyword Rules) — naming for humans (folders) and naming for search (keywords) are deliberately different vocabularies. Documentation IDs (`AI-FEAT-###`, `AI-RM-###`, `BUG-###`, `DEC-###`, `PM-###`) are permanent once assigned — never reused, never renumbered, even if the thing they name is later merged, deprecated, or superseded (`05_DOCUMENTATION_WORKFLOW.md` § Stable IDs).

## 6. UI Philosophy

The UI is a pure reflection layer: it must never mutate system state directly, must not maintain independent or derived state, and every update must originate from an explicit, validated backend state change (`docs/ui-system.md` § Principles). Selection state and preview-focus state are two separate concepts that must never be conflated — `selectedFiles` drives import/grouping, `lastClickedPath` drives preview only (`docs/ui-system.md` § Selection System). If the UI shows incorrect data, the debugging order is backend-first: verify `event.json` and `GroupManager` before touching UI code (`docs/ui-system.md` § Debugging Role) — this mirrors the same "event.json first" debugging discipline in `docs/CLAUDE.md` § Debug Protocol.

## 7. UX Philosophy

Consistency over variation, reuse over one-off styling (`docs/design-system.md` § 1, § 10). No emoji anywhere in the product UI; SVG icons only, consistent size/stroke/style (`docs/design-system.md` § 3, § 9). Interaction states are treated as a correctness surface, not decoration: the file-tile hover/selected/preview-focused states must never be visually confused with each other, and both selection and preview-focus can coexist without either implying the other (`docs/design-system.md` § 8a). Known CSS failure classes are documented as reusable lessons in the design system itself (stacking-context leaks under `backdrop-filter`, modal shell height collapse across tabs) rather than being left to be rediscovered — see `docs/design-system.md` §§ 8b, "Modals".

## 8. Performance Philosophy

Performance is a core feature, not an afterthought (`docs/performance-playbook.md` § 1). The core discipline: deterministic behavior, minimal unnecessary work, predictable scaling — and explicitly *not* premature optimization (`docs/performance-playbook.md` §§ 1, 5). The most consequential, repeatedly-learned performance rule in this codebase is IPC payload discipline: never cache a full nested IPC scan result (`_eventJson`, `imports[]`) in module-level renderer state; strip heavyweight fields before caching, load per-event data lazily (`docs/performance-playbook.md` § Layer 2b, `docs/CLAUDE.md` § Renderer Memory Safety) — this is cross-cutting, not feature-specific, and has caused real OOM crashes when violated (`01_FEATURE_REGISTRY.md` § Cross-Cutting Patterns).

## 9. Reliability Philosophy

No file is ever overwritten; conflicts rename; cleanup only happens after independently-verified copy success ([DEC-005](decisions/DEC-005_ORIGINAL_PRESERVATION_NON_DESTRUCTIVE_INGEST.md)). Copying is not equivalent to preservation, and a copy-idempotency skip is not equivalent to "nothing further needs to happen" — this distinction was learned from a real gap where same-size-skipped files had their metadata correctness never checked ([DEC-009](decisions/DEC-009_COPY_IDEMPOTENCY_MUST_NOT_SUPPRESS_METADATA_REPAIR.md), [BUG-009](bugs/BUG-009_SAME_SIZE_SKIP_METADATA_UNVERIFIED.md)). Any multi-step, long-running operation needs a persistent, resumable record of its own progress *before* it starts — proven against a real process kill (`SIGKILL`), not only a simulation ([DEC-008](decisions/DEC-008_DURABLE_METADATA_SURVIVES_RESTART.md)). Resolvers that recover from an ambiguous or incomplete hint must require *equivalent* evidence across every branch, or the hardening of one branch reintroduces the exact defect class in a sibling branch ([DEC-012](decisions/DEC-012_ARCHIVE_ROOT_RESOLUTION_REQUIRES_EVIDENCE.md)). A safety-guard bypass (like stale-lock force-clear) must stay narrowly scoped — same-device, no active conflicting operation, explicit user action, auditable outcome ([DEC-013](decisions/DEC-013_LOCK_CLEARING_MUST_BE_CONSTRAINED.md)).

## 10. Testing Philosophy

The documented stance is "practical TDD," not strict TDD everywhere: strict test-first is preferred for core logic (grouping, routing, validation, `event.json` transformations, the ingestion pipeline), while UI, Electron interactions, and filesystem operations use a validation-first approach instead (`docs/development-protocol.md` § 3). Observed practice matches this: the repository's `test/` directory contains 17 test files as of this handbook's writing, and every one of them concentrates on the metadata subsystem (`metadataExpectationService`, `metadataQueueStore`, `metadataAuditService`, `metadataRepairService`, `eventJsonStore`, RAW/XMP read-back, QMZ live E2E, field-spec consistency) — i.e., exactly the "core logic" category `development-protocol.md` prescribes TDD for. No dedicated test files exist for the renderer/UI layer, consistent with the documented "validation-first" (not test-first) treatment of UI work. This is a description of actual repository state, not a target — see [14_VALIDATION_SPECIFICATION.md](14_VALIDATION_SPECIFICATION.md) for what documentation validation (distinct from application test coverage) this system defines.

## 11. Release Philosophy

Releases are versioned tester builds (`chore(release): prepare vX.Y.Z tester build` commits bump `package.json`), each paired with a dedicated `docs/release-notes-vX.Y.Z.md` file structured as dated **Fixed**/**Added** sections plus an explicit **Notes** section that states what did *not* change (e.g. `release-notes-v0.9.8.md`: "No changes to import/copy logic... Electron security model is unchanged"). This "explicitly confirm what didn't change" habit is a real, observable discipline worth preserving — it gives a reviewer confidence about blast radius without requiring them to read the diff.

**As of AI-FEAT-057 (Part 9, 2026-08-12)**, this is no longer only inferred practice — a real, three-channel release architecture exists (`docs/product/11_ARCHITECTURAL_EVOLUTION.md` § Multi-Channel Release Architecture): Development (internal, never published), RC/Preview (real tester acceptance, opt-in, structurally isolated from Stable), and Stable (this section's own long-standing practice, unchanged). The v0.9.11 release-process incident ([PM-002](postmortems/PM-002_V0_9_11_FIRST_PUBLICATION_ATTEMPT_PRODUCED_AN_EMPTY_GITHUB_RELEASE.md)) — a real, public but empty GitHub Release, caused by `package.json`'s version drifting from the pushed tag — is what motivated turning "release discipline" from tribal knowledge into an actual hard gate (`node scripts/product-docs/cli.js release gate`, blocking, no warning-only path for a release-critical mismatch). Stable publication now additionally requires proving zero source drift from its cited verified-RC commit (excluding the version bump itself) — see [DEC-017](decisions/DEC-017_STABLE_RELEASES_REBUILD_FROM_VERIFIED_RC_SOURCE_NEVER_PROMOTE_EXACT_BINARIES.md) for why promotion rebuilds from source rather than re-uploading RC binaries.

## 12. Documentation Philosophy

Documentation must be updated alongside the work, not reconstructed from memory afterward (`05_DOCUMENTATION_WORKFLOW.md` § The Update Rule). Nothing is silently deleted — a superseded approach stays in the record, marked **rejected**/**superseded**/**deferred** with a reason (`05_DOCUMENTATION_WORKFLOW.md` § Append, Never Erase). Every factual claim must trace to code, tests, git history, existing technical docs, or current UI — or be explicitly marked **"Evidence pending"** rather than presented as a plausible-sounding guess (`05_DOCUMENTATION_WORKFLOW.md` § Evidence Discipline). `docs/product/` is authoritative for product planning and history; it is never authoritative for runtime behavior — if it and a technical doc disagree, the technical doc wins and the reconciliation gets recorded, not silently absorbed (`05_DOCUMENTATION_WORKFLOW.md` § Authority Boundary).

## 13. Decision Philosophy

A decision record exists only when a real alternative was weighed and one was chosen — not for routine implementation choices with no meaningful tradeoff (`08_DECISION_TEMPLATE.md`, `decisions/README.md`). The underlying engineering judgment predates the documentation system: patch vs. refactor vs. redesign is chosen by asking whether an issue is a symptom or a root problem, whether it's isolated or cross-module, and whether any system contract is at risk (`docs/decision-matrix.md` §§ 1–2). High-risk changes (`event.json` structure, ingestion routing, filesystem operations, anything touching a system contract) require the design to be explained and approved *before* code is written (`docs/decision-matrix.md` § 3). Where a decision record's own alternatives-considered section can't be evidenced beyond "this is what shipped," it says so explicitly rather than inventing a plausible rejected alternative (see nearly every `DEC-###`'s own "Options Considered" section for this pattern in practice).

## 14. Bug Documentation Philosophy

Not every fixed bug earns a record — only bugs whose root cause, symptom, or fix pattern would help diagnose something similar faster next time (`07_BUG_TEMPLATE.md`, `bugs/README.md`). A bug record complements, and does not replace, `docs/failure-patterns.md`'s technical symptom→cause→fix map — it carries the narrative (what was tried, what was ruled out, why the fix works) that a pure pattern table can't hold. The strongest bug records in this system so far are the recurring ones: the same architectural weakness manifesting twice in different fields is more valuable to document than either instance alone, because it proves the pattern rather than asserting it ([BUG-006](bugs/BUG-006_EVENT_EDIT_FULL_PAYLOAD_FIELD_DROP.md) is the concrete example — found for `adoption`, then independently found again for `status` three months later).

## 15. Feature Lifecycle Philosophy

A feature is documentation-complete when nothing knowable about it was left undocumented — not when every field is filled in, since some history is genuinely unrecoverable and should say so (`05_DOCUMENTATION_WORKFLOW.md` § Documentation Lifecycle Enforcement). The lifecycle is explicit and sequential: roadmap milestone → implementation → architectural evolution (when it qualifies) → decisions → bugs → rejected approaches → accepted solution → feature status → roadmap progress → changelog (`05_DOCUMENTATION_WORKFLOW.md` § The 10-step lifecycle). This produces a continuously evolving engineering history rather than a codebase with a changelog bolted on — the explicit goal stated when this lifecycle was adopted (2026-08-04, PR #1).

## 16. Documentation Automation Philosophy

Automating the *labor* of §§12–15 above (finding the right file, formatting the table, remembering to touch the changelog) is a legitimate way to keep this system alive without asking the project owner to write Markdown by hand. Automating the *judgment* in §§12–15 — deciding a bug is worth a record, deciding two options were genuinely weighed, deciding a milestone is actually done — is not, and Part 5 (`scripts/product-docs/automation/`) is built around that distinction: every "when to create a record" rule from `05_DOCUMENTATION_WORKFLOW.md` is reimplemented as an explicit, testable predicate over evidence the caller supplied, not inferred from the size or shape of a diff. A record that doesn't clear the bar is recorded as an evidence-pending candidate, never fabricated to fill a gap. This is the same evidence discipline as §12 (Documentation Philosophy), applied to a system that can now act on a session's behalf instead of only a human's.

## 17. Engineering Memory Philosophy

A canonical record (a feature file, a decision, a bug) preserves *what* is true and *what happened*; it deliberately compresses away the conversation that produced it — the drafts a plan went through, the option that looked good until a root-cause investigation ruled it out, the feedback that reshaped a design. That connective reasoning is real engineering value, and losing it the moment a session ends (a `/clear`, a closed laptop, a switch to a different AI tool) is the exact gap Part 6 (`docs/product/memory/`) exists to close — see `16_ENGINEERING_MEMORY_POLICY.md` § 1. It is explicitly *not* a second, competing source of truth: a Memory Capsule sits below every canonical record in the authority order (`16_ENGINEERING_MEMORY_POLICY.md` § 3) precisely because it answers a different question ("why did this happen this way") than a canonical record answers ("what is true now"). The same evidence discipline that governs §12 governs it too, with one addition specific to memory: where a canonical record can defer an unverifiable fact indefinitely, a capsule about a *past* conversation often has no path to recovering it at all — the honest response is the literal phrase "Evidence pending — source conversation unavailable," not a plausible-sounding reconstruction of what the conversation probably said (`16_ENGINEERING_MEMORY_POLICY.md` § 6–7). Not every session earns a capsule — the significance bar in § 8 of that policy exists so this system records engineering *stories*, not a transcript of every keystroke.

## 18. Zero-Touch Automation Philosophy

§16 draws the line between automating the *labor* of documentation discipline (legitimate) and automating the *judgment* behind it (not — every "when to create a record" rule stays an explicit, testable predicate over evidence the caller supplied). Part 7 (`scripts/product-docs/` extended, see [CLAUDE.md](CLAUDE.md) § 20) applies that same distinction one layer further: automating *when* the labor happens (at commit/push time, via version-controlled git hooks, rather than only when an agent remembers to invoke a CLI command) without automating *whether* it should happen. A pre-push hook that auto-finalizes a session does so only because the evidence gate would already have passed on its own — it never lowers the bar to make a session pass; a decision-intelligence scan that drafts a `Status: Draft` record does so only because the packet already cleared the exact same evidence bar an explicitly-reported decision would have needed. The judgment remains identical to §16's; only the trigger changed.

## 19. Repository Engineering Assistant Philosophy

`context <sub>` (Part 7E) is deliberately not a second source of truth: every bundle it returns restates the same authority order this handbook and every other document in this system already follows (technical docs under `docs/` first, canonical `docs/product/` records second, `docs/product/generated/` as locator only, `docs/product/memory/` as historical evidence, agent inference last) and points back at the canonical documents rather than substituting for reading them. Its natural-language routing (`context task`/`context explain`) uses the same deterministic keyword/alias matching `query` already used in Part 4 — no embeddings, no external model — because a tool-neutral interface any agent (Claude, Codex, Gemini, ChatGPT) can rely on needs behavior that's reproducible and inspectable, not a black box whose ranking might silently drift between vendors or model versions.

## 20. Multi-AI Conversation Integration Philosophy

Part 8 (`docs/product/conversations/`, see [18_ENGINEERING_CONVERSATION_POLICY.md](18_ENGINEERING_CONVERSATION_POLICY.md)) extends §17's answer to "why did this happen this way" past this repository's own boundary — an engineering discussion doesn't stop mattering because it happened in a browser tab instead of this terminal. The same discipline that keeps a Memory Capsule from becoming a second source of truth applies with one addition, made necessary by where the text originates: a conversation imported from outside this repository is untrusted input until it has been redacted, schema-validated, and evidence-classified, and its downstream authority is structurally capped — it may inform a canonical decision through an explicit, foreground action, but it may never trigger one automatically the way a live session's own recorded evidence can (§18's own pre-push auto-finalize). §16's significance bar has a direct Part 8 analog for the same reason it exists there: a corpus fed by external tools, potentially in bulk, needs the same "not every session/import earns a permanent record" discipline, or the record's value as a curated engineering history degrades into an uncurated one.

## What this handbook is not

It is not a source of new facts. Every claim above already existed in a cited document before this handbook was written. If a future change makes any statement here stale, fix the cited source document first, then update this handbook to match — never the reverse. This handbook also does not cover implementation-level technical detail (IPC channel names, function signatures, exact file paths) — that belongs in the routed technical docs under `docs/` (see `docs/CLAUDE.md` § Task Documentation Routing) and in the individual `AI-FEAT-###` feature files.
