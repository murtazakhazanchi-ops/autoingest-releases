## Summary

Writes a clean, archive-aware mirror of selected events from the Active Archive Root to a Transfer Drive, for physical transport to the Main Archive Root. **Why this exists** (*Known from project history; repository evidence pending* — captured during the Product-Owner Purpose Capture interview, 2026-08-14): before this capability existed, large archive transfers depended on ordinary filesystem copying — Finder, Windows Explorer, and for some transfers TeraCopy — which gave an operator no archive-aware way to know what had already been copied, what still needed copying, how to handle a destination that already had some content, or how to resume after an interruption. Real, recurring pain points included interrupted transfers, uncertainty over what had already copied, redundant re-copying, and difficulty determining destination completeness. Transfer Export replaces that blind copying with a managed workflow: it compares source and destination state, copies only what's missing, never silently overwrites existing destination content, and checkpoints its own progress so an interrupted transfer can resume. This reduces (does not eliminate) the specific risks of omission and redundant copying inherent to manual filesystem transfer — see Current Behavior for the exact mechanisms and their scope.

## Current Behavior

`services/transferExportService.js`. No-overwrite contract (AutoIngest runtime artefacts — `.autoingest/`, locks, sync queue, tmp — are excluded from the mirror). Atomic per-batch checkpoint (checkpoint granularity is per-batch, not per-file — an interruption mid-batch re-does that batch). Writes `.autoingest-transfer/exports.audit.jsonl` for traceability. Country is never part of folder names generated by export. Checksum-level verification (SHA-256, shared with AI-FEAT-025) is available via a separately-invoked `verifyExport()` step — it is **not automatic** during the copy itself, which only checks file size; this is a deliberate speed/cost tradeoff, not a gap (confirmed by product-owner decision, 2026-08-14).

**Concurrency note** (confirmed 2026-08-14, forensic code verification — see [DEC-021](../decisions/DEC-021_TRANSFER_EXPORT_PROCESS_LOCAL_LOCK_ACCEPTED_FOR_PRESENT_OPERATIONAL_MODEL.md)): the transfer-running guard (`_state.running`) is an **in-memory, process-local flag** scoped to a single running app instance. It prevents two Export operations from overlapping *within the same app process*, but is **not** a durable, cross-device lock and does **not** share any mechanism with AI-FEAT-045's `archiveLockService.js` (SHA1-keyed, TTL+heartbeat, event/photographer-scoped) — this resolves what an earlier `autoingest-architect` review had flagged as unconfirmed. Two independent AutoIngest instances on two different machines could, in principle, run Transfer Export against the same physical destination simultaneously without this guard preventing it. This is an accepted limitation for the present operational model, not an oversight — see DEC-021.

## Future Enhancements

**Durable, destination-level / cross-device locking** — recorded per DEC-021 as a future reliability enhancement, not scheduled or implemented. The longer-term architectural direction is that AutoIngest should be able to protect against the uncommon case where two independent AutoIngest instances attempt to operate on the same transfer destination simultaneously; the current process-local guard does not provide this. `docs/archive-operations-layer.md` § Known Limitations also notes "No bulk adoption: events are adopted one at a time" (relevant to AI-FEAT-046, not this feature directly).
