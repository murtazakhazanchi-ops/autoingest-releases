## Symptom

Creating a new event from inside an active Import workspace (via "Change Event → create new event") produced the event's root folder and both of its sub-component folders on disk, but **no `event.json` anywhere inside the event folder** — both sub-component folders were also completely empty. Event Management then listed the event as a **"legacy event"** (no readable `event.json`). Attempting to use Event Management's own "fix this legacy event" repair flow on it also did not produce an `event.json` — the repair appeared to do nothing, silently.

## Root Cause

`_tryCreateEvent()` (`renderer/eventCreator.js`) wrote `event.json` to `activeMaster.path + '/' + safe`, but created the event's sub-component folders at a **separately re-derived** path: `(coll._masterPath || activeMaster.path) + '/' + safe`. These two expressions are not guaranteed to agree. `coll._masterPath` is deliberately repointed at a local-staging path whenever the archive is perceived as offline/invalid (`archive:getOperationsStatus` returning `'nas-disconnected'` or `'invalid-nas'`), while `activeMaster.path` is deliberately *kept* pointing at the archive path even while offline, so a later retry can detect the NAS becoming reachable again (see the existing `_effectiveCollPath()` resolver's own comment). Nothing re-synchronizes `coll._masterPath` back to the archive path once the archive becomes reachable again mid-session. Confirmed live: the test archive folder used for the repro had no `.autoingest/root/archive-root.json` marker, which `main.js` treats as `'invalid-nas'` — exactly the trigger condition, since this ad-hoc local test folder was never run through the app's own root-initialization flow.

Consequence once the archive is reachable again but `coll._masterPath` is still stale: the primary `event.json` write succeeds against the archive path; the sub-component folders then get created at the stale/staging path instead — a *different* physical folder for the same logical event. `getActiveEventData()` (which every downstream reader, including the workspace-return flow and Event Management's own scan, ultimately consults) read `coll._masterPath` directly, landing on the sub-folder/staging-side location, finding no `event.json` there, and correctly (from its own point of view) reporting the event as unreadable/legacy.

The "fix legacy event" repair flow (`_tryRepairEvent()`) had the identical divergence — it used `activeMaster.path` exclusively, never the same resolver `_scanAndRenderEventList()` used to discover and list the legacy entry in the first place — so a repair attempt targeted a different (often nonexistent, or newly-created-and-empty) folder than the one actually showing as legacy. Independently, `_tryRepairEvent()`'s `writeEventJson()` call was fire-and-forget (`.catch(err => console.error(...))` only, never awaited), so even when the path happened to be right, a write failure was never surfaced to the operator — the repair could silently do nothing while the UI proceeded as if it had succeeded.

Here the write itself never lands in the right place. Confirmed via `grep -rliE` across `docs/product/bugs/` that no existing record matched this symptom.
- **2026-10-13** — Dispatched a `contract-debugger` subagent for read-only root-cause tracing (per `docs/CLAUDE.md`'s Agent Selection Routing — "Debugging / stabilization / contract failures / root-cause tracing → contract-debugger"). It traced `_effectiveCollPath()` (the one correct, already-used-elsewhere resolver), found the two independent path-derivation expressions in `_tryCreateEvent()` and the `activeMaster.path`-only expression in `_tryRepairEvent()`, identified the unawaited-write defect in the repair flow, and flagged two secondary (not primary-cause) hardening gaps in `main.js`'s `event:write` IPC handler (folder `mkdir` happens before `eventData` validation; a throw from a best-effort post-write notification can mask an already-successful write as a failure).
- **2026-10-13** — Independently re-verified the agent's one open item myself: confirmed via direct filesystem check that the test archive folder (`/Users/funun_pa/Desktop/ai-test-archive-2/`) genuinely has no `.autoingest/root/archive-root.json` marker, corroborating the `invalid-nas` trigger condition the investigation predicted, before authorizing a fix.

## Fix

`renderer/eventCreator.js`, on a dedicated branch (`fix/event-json-path-divergence`, off `main`, commit `f09890f` — deliberately *not* on `feature/mx-creative-console-v2`, since this bug and its fix are unrelated to that feature):

- **`_tryCreateEvent()`**: captures whichever success branch's write actually landed (`_actualEventFolderPath` — either the primary `eventFolderPath` or the offline-fallback `_stagingEvPath`) into one local variable, and uses that exact value for sub-component folder creation instead of independently re-deriving `coll._masterPath || activeMaster.path`.
- **`_tryRepairEvent()`**: resolves the rename/write target via the existing `_effectiveCollPath() || activeMaster.path` resolver — the same one `_scanAndRenderEventList()` already uses — instead of `activeMaster.path` alone. The `writeEventJson()` call is now awaited and its result checked; on failure, `_showEventBanner()` surfaces an error and the function returns *before* touching the `_scannedEvents` cache or resetting UI state, so the UI never shows a "repaired" event that doesn't actually have an `event.json` on disk.
- **`getActiveEventData()`**: resolves `collectionPath` via `_effectiveCollPath()` instead of the bare `coll._masterPath`, so every downstream consumer (`reloadForImport`, `loadEventSnapshot`, the workspace-return flow, Event Management's scan) is guaranteed to agree on where a collection actually lives, now that the writes above land exactly there.

Validated by temporarily applying the identical patch to `feature/mx-creative-console-v2` (confirmed via `git diff main feature/mx-creative-console-v2 -- renderer/eventCreator.js` that the three touched functions are untouched by that branch's own changes, so this is a faithful test of this exact change) and running the two existing live tests that exercise this machinery end to end: `test/multiEventNewEventUiLive.test.js` (online create-from-workspace) and `test/multiEventLocalFirstUiLive.test.js` (three events created under forced offline/Local-First staging). Both passed cleanly, unchanged. The patch was then reverted from that branch — nothing from it is part of this fix's commit.

Not fixed in this change (flagged as separate, independent hardening, deliberately out of scope for this minimal fix): `main.js`'s `event:write` handler creates the event folder before validating `eventData`, which can leave an orphaned empty folder behind on a validation failure; and it wraps the durable write and the best-effort `realtimeOps.emitEventVisible`/`emitRegistryEvent` calls in the same `try`/`catch`, so a throw from the notification step *after* a successful write is reported back to the caller as a write failure.

## Prevention / Reusable Lesson

When a feature introduces a second notion of "the current path" for state that must agree with a first, pre-existing notion (here: `coll._masterPath` alongside `activeMaster.path`, with an already-correct unifying resolver, `_effectiveCollPath()`, sitting right next to both) — audit every call site that derives that path independently, not just the one the new feature itself added. The unifying resolver already existed and was already used correctly by `_scanAndRenderEventList()`; the bug was that two *other*, older call sites (`_tryCreateEvent()`'s sub-folder creation, `_tryRepairEvent()`'s rename/write) never routed through it. This is the same class of bug as `docs/failure-patterns.md` #11 ("State Desync — multiple sources of truth") — consider adding "two independently-derived path/state variables that are expected to stay equal, with no resync point, diverging after an offline/error episode" as a named sub-pattern there if a third instance of this shape appears.

Separately: a fire-and-forget write (`.catch(console.error)` with no await, no UI-facing failure path) inside a user-initiated "repair"/"fix this" action is a direct violation of this project's "never silently swallow errors" rule, and is worth grep-ing for (`window.api.write.*\(.*\)\s*\.catch\(.*console\.error`) elsewhere in `renderer/` as a follow-up audit, independent of this specific bug.
