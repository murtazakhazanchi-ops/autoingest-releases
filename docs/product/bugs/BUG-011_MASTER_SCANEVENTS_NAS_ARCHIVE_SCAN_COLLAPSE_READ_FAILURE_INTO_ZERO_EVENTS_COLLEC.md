## Symptom

Event Management showed "Existing Events (0)" / "No resolvable events yet." for a collection that physically contained a valid, event.json-backed event on the NAS archive. The same collection sometimes showed its events correctly and sometimes did not, on the same machine and archive, with nothing about the archive itself changing.

## Root Cause

**Final confirmed root cause (2026-08-11 — this is the defect that actually produced every real-world "Existing Events (0)" report on the tester's Windows/NAS hardware):** `main/main.js`'s `_scanEventsCore` (the implementation behind `master:scanEvents`) computed each event's `sequence` field from one of two producers with different runtime types — `parseEventName()` always yields a 2-digit zero-padded **string** (e.g. `"01"`) when a folder's name parses successfully, but whenever a folder's name failed to parse (e.g. an unrecognized city token not present in the currently-configured `data/cities.json`), the code fell back to `eventJson.sequence` — a value read straight from the persisted `event.json`, which is a **number** whenever it was written by the Create/Edit Event form (the form always calls `parseInt(seq, 10)` before writing). When `resolved.sort()` then ran its comparator (`b.sequence.localeCompare(a.sequence)`) across a collection containing both kinds of entries, `String.prototype.localeCompare` threw `TypeError: b.sequence.localeCompare is not a function` the moment a number ended up as the comparator's receiver. This exception was thrown from *inside* `master:scanEvents`, **after filesystem discovery and event.json parsing for every entry had already completed successfully** (confirmed via the real tester's `app.log`: all 52 entries logged `READ_EVENT_JSON_OK` before the crash) — the entire successfully-discovered result set was then lost because the unhandled exception aborted the whole IPC request rather than returning the events already gathered. The fix (see Fix section below) normalizes `sequence` to the canonical zero-padded string at the single point it is first computed, before it can ever reach the comparator in a mismatched state. Full producer audit, investigation timeline, and regression tests are in the Investigation Log and Fix section below.

**Original hypothesis (2026-08-07 — investigated, real, but NOT what the tester actually hit; retained for historical accuracy per this system's append-never-erase policy):** `main/main.js`'s `master:scanEvents` IPC handler caught ANY `fsp.readdir()` failure — including transient NAS/SMB read errors (permission blips, timeouts, disconnects) that have nothing to do with the collection's actual contents — and returned a bare empty array, identical to what a genuinely empty collection returns. The renderer (`eventCreator.js`'s `_scanAndRenderEventList`) had no way to distinguish "scan failed" from "confirmed empty" and rendered the error case as "No resolvable events yet." The sibling NAS-wide scanner, `_scanNasArchive`/`_runNasScan`, had the same defect one level up: a marker-file read failure that was not `ENOENT` was reported as `'invalid-nas'` (implying a misconfigured archive) instead of a transient-unreachable state, and a readdir failure on a single collection folder mid-scan silently produced a collection entry with `events: []` and no error flag at all. This defect was real and was fixed (see Fix section — the `{ok, events, errorReason}` shape change), but the 2026-08-08 real-hardware RC verification proved it was not the cause of the tester's actual "(0)" symptom; the investigation continued past this fix until the true root cause above was found on 2026-08-11.

- **2026-08-11 — ROOT CAUSE CONFIRMED: mixed `sequence` type crashes `resolved.sort()` with `TypeError: b.sequence.localeCompare is not a function`, thrown from inside `master:scanEvents` after all 52 entries were successfully discovered.** The real tester `app.log`, captured via the IPC-boundary instrumentation shipped the previous round, shows the exact exception across 3 separate scan attempts, all identical: `POST_LOOP_START` → `SORT_START` → `[EventDiscoveryIPC] phase=IPC_HANDLER_ERROR error="b.sequence.localeCompare is not a function"` → `[EventDiscoveryRenderer] phase=RENDERER_SCAN_INVOKE_ERROR error="Error invoking remote method 'master:scanEvents': TypeError: b.sequence.localeCompare is not a function"`. This is **platform-independent JS type coercion**, not a Windows/SMB/IPC defect — every filesystem, IPC-boundary, and structured-clone hypothesis from the two prior rounds was correctly ruled out by their respective audits; the crash simply lives one step later than any of them looked, in application-level sort logic, and only manifested on the real Windows archive because that's where a folder with a `parseEventName()`-unparseable name (a folder name whose city token isn't in the currently-configured `data/cities.json`) happened to exist alongside normally-named events.

  **Why `sequence` can legally be a string, a number, or undefined** (`main/main.js`'s `_scanEventsCore`, the code this bug lives in):
  ```js
  const sequence = parsed.ok ? parsed.sequence : (eventJson.sequence || '00');
  ```
  - `parsed.sequence` (from `main/eventNameParser.js:97`'s `PREFIX_RE = /^(\d{4}-\d{2}-\d{2}) _(\d{2})-(.+)$/` regex capture) is **always a 2-digit zero-padded string** — regex capture groups are inherently strings, and the pattern enforces exactly 2 digits. This is used whenever `parseEventName()` succeeds (`parsed.ok === true`) — the overwhelmingly common case for any normally-named folder, which is exactly why every synthetic fixture built across the previous two rounds of this investigation (all using normally-parseable names) never reproduced this.
  - `eventJson.sequence` (from `JSON.parse()` of the file on disk) is used **only** when `parsed.ok === false` — i.e. the folder's own name fails to parse (invalid date/seq prefix, or no token in it matches the currently-configured cities/locations lists — `parseEventName()` returns `{ok:false}` with no `hijriDate`/`sequence` fields at all in that case, confirmed by reading `eventNameParser.js` directly). Its type is whatever was last persisted to disk — see the producer audit below.
  - `undefined`/falsy `eventJson.sequence` is guarded by the `|| '00'` fallback, which coerces it to the *string* `'00'` before it ever reaches the sort — so a missing sequence value never itself causes this crash (confirmed: `undefined` is a legal transient value here, but only ever surfaces as the string `'00'`).

## Prevention / Reusable Lesson

Any IPC handler that reads a NAS/UNC path must never collapse a caught filesystem error into the same shape as "confirmed empty" — return an explicit ok/error signal so the renderer can distinguish "nothing here" from "could not check." When adding a second layer that validates a precondition before calling a lower-level scan function (e.g. _runNasScan validating the marker before calling _scanNasArchive), the lower-level function can safely assume that precondition already holds and should not re-guess "invalid" from a bare readdir failure.

When a value can legally arrive as more than one type from different producers (here: a regex-derived string vs. a JSON-persisted number), normalize it once, at the earliest point it's computed — not at every comparator/consumer that happens to need a specific type. A validator that deliberately accepts multiple types (`isValidEventJson`'s `typeof obj.sequence === 'number' ? ... : parseInt(...)`) is a signal the type was never fully decided, not a substitute for deciding it. When the identical value already has a correct, working normalization pattern elsewhere in the same file (here: `_scanNasArchive`), a sibling function computing the same value without it is very likely an oversight worth searching for directly, not a novel problem to solve from scratch. And when regression-testing a comparator bug, remember that `Array.prototype.sort()`'s comparator call order is input-order-dependent — a live end-to-end test can pass for the wrong reason depending on which of a mismatched pair a sort algorithm happens to place in which argument position; test the comparator directly, in every argument order, for a proof that doesn't depend on the sort algorithm's internal behavior.
