# Changelog — docs/product/

This is a log of changes to the **documentation system itself** (registry entries added/changed, roadmap milestones moved, major restructuring) — not a user-facing release changelog. For user-facing release notes, see `docs/release-notes-*.md`.

Append newest first. Never edit or delete a prior entry — if something was wrong, add a correcting entry.

## 2026-08-05 — Part 4: Queryable Documentation & Engineering Intelligence

- **Repository-local tooling added**: `scripts/product-docs/` — plain Node.js (CommonJS, no build step, no new npm dependencies, `package.json` untouched), matching the existing `scripts/validate-event-metadata.js` convention. Commands: `build`, `validate`, `query`, `impact`, `changes`, `all`, each with `--help`. See [scripts/product-docs/README.md](../../scripts/product-docs/README.md) for the full authority model, query-ranking algorithm, and ownership-resolution rules (`explicit`/`inferred`/`unknown` — never a filename-pattern guess).
- **Generated output added**: `docs/product/generated/` (tracked in git, unlike the ignored `docs/product/exports/`) — `feature-index.json`/`.jsonl`, `search-index.jsonl`, `authority-index.json`/`AUTHORITY_INDEX.md`, `subsystem-locator.json`/`SUBSYSTEM_LOCATOR.md` (16 subsystems derived from `01_FEATURE_REGISTRY.md`'s category headers), `dependency-graph.json`/`.md` (with bounded per-subsystem Mermaid views, not one unreadable graph), one `feature-timelines/AI-FEAT-###_TIMELINE.md` per feature (strictly extracted from each feature's own Evolution/Implementation Journal — no new facts), `roadmap-dashboard.json`/`.md`, `documentation-health.json`/`.md`, `change-reports/*`, and `manifest.json` (carrying `docsys_version`, `schema_version`, `source_commit`, `generation_command`, entity/relationship counts).
- **Documentation-system version introduced**: `DOCSYS_VERSION 1.0.0` (`scripts/product-docs/lib/version.js`), distinct from the application's `package.json` version and from the `AI-FEAT-###`/`AI-RM-###` ID systems.
- **`14_VALIDATION_SPECIFICATION.md`'s 13 rules now have a first real, runnable implementation** (`scripts/product-docs/lib/validators.js`, invoked via `validate`), plus Part 4's own tooling-integrity checks beyond the original 13: schema validity (a small dependency-free JSON Schema subset validator, not `ajv`), dependency-graph edge integrity (no edge may reference a nonexistent node), undocumented dependency cycles, generated-output freshness (a committed `docs/product/generated/` file that doesn't match a fresh in-memory rebuild is an `error`-level `stale-generated-output` finding), registry/file mismatches, and ambiguous-alias detection. Findings are classified error/warning/information/evidence_gap; only errors fail the build, matching `14_VALIDATION_SPECIFICATION.md`'s own stated policy.
- **Authority model formalized as three tiers**: technical docs under `docs/` > canonical Markdown under `docs/product/` > `docs/product/generated/` (a locator only, never a source of new facts, freshness-enforced by `validate` rather than merely assumed). `12_DEPENDENCY_MODEL.md` received a one-paragraph disambiguation note distinguishing its curated narrative from `generated/dependency-graph.*`'s mechanically-derived subsystem/code-level view — the two are not duplicates and neither supersedes the other.
- **AI agent workflow codified**: `CLAUDE.md` §14a — query the authority index, identify `AI-FEAT-###` IDs, read canonical docs directly (never stop at the generated summary), run `impact` before changing anything, update canonical records during implementation, then `build`/`validate` before the commit. `05_DOCUMENTATION_WORKFLOW.md`'s Update Rule and 10-step lifecycle both gained a pointer to this same `build && validate` step.
- **Stale dashboard narrative found and corrected** (not silently — a `stale-dashboard-narrative` validator check flagged it first, and this changelog entry records what changed and why, per this system's own Evidence Discipline rule): `04_PROJECT_DASHBOARD.md`'s "Current branch," "Latest relevant commit," and "Documentation system status" fields described Part 3 as uncommitted and in-progress on a feature branch, even though Part 3 (`bd767d4`) was already merged to `main` by the time this Part 4 pass began. Corrected to state the actual branch (`main`) and commit, and to describe Part 4 by what it delivered and when rather than by commit status (to avoid the same field going stale again the moment this itself is committed). The correction touched only narrative/status fields — "Overall roadmap progress," "Completed roadmap milestones," "Current roadmap milestone," and every other roadmap-progress field were left untouched, since documentation-tooling progress must never be conflated with AutoIngest application roadmap progress.
- **Two real correctness bugs found by code review and fixed before commit**: (1) `lib/ids.js`'s ID extraction only captured the two endpoints of an "A through B" / "A – B" prose range (a convention used throughout `docs/product/`, e.g. `11_ARCHITECTURAL_EVOLUTION.md` §5's "AI-FEAT-049 – AI-FEAT-056," `DEC-015`'s "AI-RM-002 through AI-RM-009") — every interior ID silently vanished from generated indexes; `documentation-health.md`'s architecture-coverage finding was misreporting `AI-FEAT-050`–`055` as unplaced despite `11_ARCHITECTURAL_EVOLUTION.md` explicitly placing them via that range. Fixed with explicit range expansion, capped at a 500-ID span as a sanity guard. (2) `lib/dependencyGraph.js`'s decision-record `governed_by` edges only extracted the `feature` ID family from `decisions/*.md`'s `Related feature(s) / roadmap milestone` header field, even though that field legitimately mixes both families (`DEC-007`→`AI-RM-001`, `DEC-008`→`AI-RM-001`, `DEC-015`→`AI-RM-002`…`009`) — every milestone edge from a decision was silently absent from `dependency-graph.json`/`.md`. Fixed by extracting both families from that field.
- **One defensive hardening applied on code review**: `lib/gitInfo.js`'s git shell-outs now reject any ref argument starting with `-` before use (closes a theoretical git argument-injection class on the `changes <fromRef> <toRef>` command) and set an explicit 64MB `maxBuffer` (Node's un-overridden default is 1MB, which a pathologically large ref range could exceed).
- **Validated against the real repository** (after the fixes above): all 56 `AI-FEAT-###` records, all 9 `AI-RM-###` milestones, all 10 `BUG-###`, 15 `DEC-###`, and 1 `PM-###` record parse and appear in the generated indexes; zero dangling dependency-graph edges; zero `error`-level `validate` findings; deterministic rebuild (two successive `build` runs from the same source commit produce byte-identical output); the generated roadmap dashboard's current-position statement (`AI-RM-001` complete, `AI-RM-002` next, 1/9 milestones) matches `02_MASTER_ROADMAP.md` and `04_PROJECT_DASHBOARD.md` exactly.
- **60 tooling tests added** under `scripts/product-docs/test/` (`node:assert`, matching the repository's existing `test/*.test.js` pattern; a shared `testHarness.js` extracted since this directory has several test files). Isolated synthetic fixtures under `test/fixtures/broken-product-docs/` for validator-rule tests (never mutates the real `docs/product/` tree); a read-only integration suite against the real tree for whole-repository invariants.
- Reviewed by `autoingest-architect` and `documentation-update-specialist` (design phase, read-only) and `code-reviewer` and `performance-auditor` (implementation phase, read-only) — all four completed and findings above were applied; the performance audit found no algorithmic scaling cliff and confirmed the tool's git operations are correctly left unscoped to `docs/product/` (needed for source-file cross-referencing), recommending only the `maxBuffer` fix applied above.
- No application/runtime code changed. `package.json` and `package-lock.json` were not modified.

## 2026-08-04 — Part 3: Documentation Intelligence & Lifecycle System

- **Phase 1 — Complete Feature Lifecycle Model**: added a mechanically-generated **Lifecycle Metadata** section to all 56 `features/AI-FEAT-###_*.md` files, covering Related features (beyond Dependencies/Parent/Subfeatures), Related decisions/bugs/postmortems (union of forward links already in the file and reverse lookups from each record's own `Related feature(s)` field), Related architectural-evolution sections, Related release notes, Testing coverage, and a computed Documentation completeness indicator. No field was invented — every value is either copied from an existing header field, discovered via reverse lookup against an existing record, or mechanically derived from `test/` and `docs/release-notes-*.md` file listings, with "Evidence pending" used wherever no match was found.
- **Phase 2 — Dependency Intelligence**: added [12_DEPENDENCY_MODEL.md](12_DEPENDENCY_MODEL.md), a canonical relationship index covering Milestone→Features, Decision→Decision, Bug→Decision, Bug→Bug, Architecture→Features/Decisions/Postmortems, and Feature→Postmortem — all derived from citations already present in existing records, with a coverage census (not a completeness requirement) at the end.
- **Phase 3 — Engineering Evolution**: added an **Engineering Evolution** section to all 56 feature files, classifying each feature's already-evidenced history (Initial implementation, Architectural/workflow decisions, Reliability/correctness fixes, Other dated milestones) by pointing back to the existing Evolution/Implementation Journal, Decisions, and Known Bugs sections rather than restating them — deliberately not a second changelog.
- **Phase 4 — Documentation Lifecycle Enforcement**: extended [05_DOCUMENTATION_WORKFLOW.md](05_DOCUMENTATION_WORKFLOW.md) with a formal 10-step lifecycle table, a "fields you're obligated to keep current" list, and an explicit Definition of "documentation complete" for a feature.
- **Phase 5 — Engineering Handbook**: added [13_ENGINEERING_HANDBOOK.md](13_ENGINEERING_HANDBOOK.md), 15 philosophy sections (application, digital archival, metadata, folder hierarchy, naming, UI, UX, performance, reliability, testing, release, documentation, decision, bug-documentation, feature-lifecycle), every claim cited to an existing decision or technical doc — no aspirational statements unsupported by the repository.
- **Phase 6 — Validation System**: added [14_VALIDATION_SPECIFICATION.md](14_VALIDATION_SPECIFICATION.md), 13 validation rules (duplicate IDs, broken links, missing roadmap/feature references, orphan bugs/decisions/postmortems, missing architecture/changelog references, implemented-without-documentation, planned-without-roadmap, roadmap inconsistencies, documentation-completeness gaps) — specification only, no executable tooling checked in, per explicit instruction. Every rule's "Verified in practice" line cites when this exact check was actually run by hand during this system's own construction.
- **Phase 7 — AI Operating System**: rewrote [CLAUDE.md](CLAUDE.md) from a short routing file into the full operating manual — documentation hierarchy, authority boundaries, routing, feature lifecycle, documentation lifecycle, evidence standards, cross-linking rules, planning methodology, engineering philosophy, decision philosophy, historical preservation, bug/postmortem documentation standards, validation expectations, update workflow, release workflow, and future feature workflow.
- Updated `docs/product/README.md` (new files listed, authority section extended) and `04_PROJECT_DASHBOARD.md` (documentation-system status only — roadmap position unchanged, since no implementation work occurred).
- Fixed one self-inflicted false-positive in the documentation link-checker script: `14_VALIDATION_SPECIFICATION.md`'s own prose describing the link-check rule used bracket-paren example syntax that the checker itself flagged; reworded to avoid the ambiguity.
- No application/runtime code changed.
