## Context

Stage 3/3.1 qualified the isolated Qwen runtime (`services/qwenRuntime/runtime.js`/`runtimeWorker.js`) as a simple prompt-in/text-out API across an Electron `utilityProcess` boundary — it has no tool-calling support. Stage 2 productionized five deterministic Knowledge operations (`scripts/product-docs/lib/askKnowledge/`) and Stage 1 productionized deterministic retrieval (`scripts/product-docs/lib/askRetrieval/`) as plain, dependency-light JS functions with zero production callers. The C9-C14 experimental bench lineage separately prototyped a full tool-calling conversational engine, entirely in-process (no isolation at all), against these same knowledge operations' *pre-production* precursor (`knowledgeAccessC9..C14.js`) — superseded by Stage 2's own promotion of that logic into production.

Stage 4 authorizes building the first production one-brain conversational orchestrator connecting all three. This requires resolving two architectural questions Stage 3 never had to answer.

## Decision 1 — Where does tool-calling capability live?

**Options considered:**

1. **A second, parallel Qwen-loading child process dedicated to conversations**, separate from Stage 3's own `runtimeWorker.js`. Rejected: this creates a SECOND place in the codebase capable of loading a Qwen model instance, which directly works against the one-brain invariant's own mechanical guarantee (the invariant is easiest to prove when there is exactly one code path that can ever spawn a Qwen-loaded process) rather than reinforcing it. It would also duplicate Stage 3's already-qualified model-load/context-creation/cancellation/crash-recovery machinery for no benefit.
2. **Extend the already-qualified `services/qwenRuntime/runtime.js`/`runtimeWorker.js` with new message types for conversational tool-calling** (chosen). The existing simple `load`/`infer`/`unload`/`createContext`/`disposeContext`/`diagnostics` protocol is left completely unchanged (Stage 3.1's own qualification harness continues to exercise it exactly as before); new message types (`createSession`/`session-created`, `promptSession`/`session-result`, `resetSession`/`session-reset`, `disposeSession`/`session-disposed`, `getSessionHistory`/`setSessionHistory`, plus the `tool-call`/`tool-result` pair carrying each individual tool invocation across the process boundary — see Decision 2) are added alongside them, sharing the SAME loaded model/context, the SAME FIFO queue discipline, the SAME "stop waiting, don't interrupt native generation" cancellation strategy, and the SAME crash-recovery behavior already qualified. This is a genuine, authorized extension of Stage 3's own scope (Section 3 of the Stage 4 brief explicitly frames `services/qwenRuntime/` as a foundation to build on), not a violation of "never modify already-qualified files" — that principle exists to protect *unrelated* production infrastructure from incidental changes, not to freeze a stage's own code against its own next authorized stage.

## Decision 2 — Where do tool handlers execute?

**Options considered:**

1. **Tool handlers execute inside the isolated child process itself, alongside node-llama-cpp.** `scripts/product-docs/lib/askKnowledge/` and `scripts/product-docs/lib/askRetrieval/` are pure, dependency-light JS with zero Electron or native requirements — proven directly by their own Stage 1/2 test suites, which already run them standalone under plain `node` — so this was a genuinely viable option, not a strawman. Rejected in favor of option 2 below: it would require the isolated child to additionally load and hold the entire Knowledge Base corpus (`build.assemble()`'s generated-index data) for the life of the process, entangling two previously-independent concerns (pure Qwen runtime mechanics vs. deterministic Knowledge Base state) inside the one process Stage 3 deliberately kept narrow, for a latency saving that measured as immaterial in practice (see below).
2. **A parent↔child RPC bridge: the child's tool `handler`s message the parent (main process) to actually run `search_autoingest`/`read_autoingest`/etc., await a correlated response, then return it into node-llama-cpp's function-calling loop** (chosen). `services/qwenRuntime/runtime.js` gains `registerSessionToolHandlers(sessionId, handlers)`; `runtimeWorker.js`'s own tool `handler`s are thin proxies that `postMessage({type:'tool-call', ...})` and await the matching `{type:'tool-result', ...}`. This keeps the isolated child's own crash-sensitive surface EXACTLY as narrow as Stage 3/3.1 already qualified it — zero Knowledge Base code or data ever enters that process — at the cost of one additional same-machine IPC round-trip per tool call, which is negligible relative to the tens/hundreds of milliseconds a real tool call or a generation step already takes. The entire tool-calling loop is still an internal `while`-style loop inside node-llama-cpp's own `promptWithMeta` (confirmed directly from the installed 3.20.0 source and from `engineC14.js`'s own forensic trace of it) — the parent sends one `promptSession` message per operator turn and receives one structured `session-result` back, regardless of how many tool calls happened inside; only each individual tool call's own execution crosses the process boundary, not the loop itself.

## Decision 3 — Tool-calling API shape

Verified directly against node-llama-cpp 3.20.0's own `.d.ts` files, not assumed: `defineChatSessionFunction({description, params, handler})` where `params` is a GBNF-JSON-schema-compatible object (a JSON-schema-like shape constrained to what GBNF grammars can express — string/number/boolean/object/array/enum, no arbitrary `oneOf`/`$ref` complexity) and `handler: (params) => Promise<any> | any`. `LlamaChatSession.promptWithMeta(prompt, {functions, maxTokens, ...})` returns `{responseText, stopReason}` where `stopReason` is one of `"abort" | "maxTokens" | "eogToken" | "stopGenerationTrigger" | "functionCalls" | "customStopTrigger"`. `promptWithMeta` does accept `signal`/`stopOnAbortSignal` directly — deliberately NOT used, per the same SIGBUS/Metal finding this project has carried since Gemma's own runtime (DEC-025): cancellation remains "stop waiting," never "interrupt native generation," now applied at the orchestrator/turn level exactly as `runtime.js`'s own `infer()` already does at the single-inference level.

## Decision 5 — Context budget and history management (Section 15/16)

`contextSize = 24576` (Stage 3's own pinned value, per-sequence, unchanged). node-llama-cpp's `LlamaChatSession` already runs its own built-in `contextShift` (default strategy `"eraseFirstResponseAndKeepFirstSystem"`) whenever the context fills — this is a real, already-implemented deterministic pruning mechanism, not something Stage 4 needs to reinvent. Stage 4 adds only: (a) approximate turn/token accounting for diagnostics, surfaced per Section 32; (b) a last-resort recovery path for the (expected to be rare) case where `contextShift` itself cannot make room — a fresh `LlamaChatSession` is created on a fresh sequence, with a short deterministic system note that earlier conversation content is no longer available, rather than a raw exception or a silently corrupted session. No second learned model or self-summarization step is used anywhere in this path, per Section 16's explicit prohibition.

## Consequences

- `services/qwenRuntime/runtimeWorker.js` and `runtime.js` grow in scope beyond "simple single-shot inference" to also host conversational tool-calling (session create/prompt/reset/dispose, history get/set, tool-call/tool-result relaying) — a deliberate, documented extension of Stage 3, not scope creep into Stage 5 (no IPC/preload/renderer/UI change accompanies it).
- All new conversational-policy logic (tool descriptions, system prompt, the final-answer validator, context-budget/history-pruning policy, the bounded tool-action loop, duplicate-call protection, regeneration/fallback, per-session diagnostics) lives in a new `services/qwenOrchestrator/` module sitting on top of the extended `runtime.js` — per Decision 2, tool EXECUTION itself also happens in this same orchestrator/main process (never inside the isolated Qwen child), mirroring the same "new parallel modules, existing infrastructure's design pattern reused, not its code" discipline this project has followed since Stage 2.
- Stage 2's `roadmap_status(handle)` real signature (handle-or-empty) is used as-is; the production tool description explains this exactly, rather than reintroducing the bench prototype's free-text `query` parameter that no longer matches the real function.

## Postscript — Independent Review Findings (2026-09-06)

The implementation above was built, then independently reviewed against the running codebase and node-llama-cpp's own installed `.d.ts` files line by line before being trusted. The review found and fixed three real gaps, none large enough to change any Decision above, all now closed with dedicated tests:

1. **Crash-safety gap in the five new `runtime.js` session functions.** `createSession`/`resetSession`/`getSessionHistory`/`setSessionHistory`/`disposeSession` each awaited a one-shot ad hoc `_child.on('message', ...)` listener with no entry in `_pending`/`_pendingSessions` — unlike those two maps (which `_reset()` already rejects on a real child crash), a crash mid-request on any of these five would never settle, and because every one of them runs inside the shared `_enqueue()` FIFO queue, a permanently-unsettled promise would wedge the ENTIRE runtime (all future `infer()`/session calls, not just that one request) forever. Fixed with a small `_pendingChildOps` registry (`_awaitChildMessage()`) that `_reset()` now also rejects on crash, scoped entirely to these five new functions — Stage 3's own original `load`/`createContext`/`disposeContext`/`unload` are untouched.
2. **`containProtocolArtifacts` (the promoted Qwen-family control-token stripper) was written, exported, and had zero test coverage and zero call sites** — a real gap between this decision's own PROMOTE classification and the actual wiring. Now applied unconditionally in `session.js`'s `sendMessage()`, before every validation pass (initial and each regeneration), as the disclosed defense-in-depth backstop it was always meant to be; two new tests cover the standalone function and its live wiring.
3. **Section 32's required "context token usage" diagnostics field did not exist.** `pruneHistoryToFit()` already computes this figure as part of its own budget decision (`contextBudget.js`'s `computeBudget()`); it is now surfaced as `getDiagnostics().contextTokenUsage` after every turn, at no extra measurement cost, with a dedicated test.

All three fixes are additive to files this stage already owns (`runtime.js`'s Stage-4 session extension, `session.js`) — no Stage 3/3.1 behavior changed, confirmed by the full pre-existing regression suite (56 Stage-3/3.1 tests, unchanged) plus 56 orchestrator tests (up from 51 before the fixes).

## Postscript — Real-Model Qualification (2026-09-06)

Real-model qualification was run via a new permanent harness (`services/qwenOrchestrator/electronQualificationHarness.js`, mirroring `services/qwenRuntime/electronSmokeTest.js`), against the same real, SHA-256-verified Qwen artifact Stage 3.1 qualified, through the real `OrchestratorSession`/`runtime.js`/`runtimeWorker.js` stack end to end — never a mock or a bypass.

**A severe, disclosed environmental constraint on this development machine** repeatedly slowed this qualification far below the runtime's own true latency: `top`/`ps` measurement during the session showed system-wide memory usage fluctuating between roughly 30–35 GiB of 36 GiB total (as low as ~240 MiB free, unrelated to anything this stage's own code held), driven by factors outside this session's control (concurrent activity on a shared, actively-used development machine). Under a verified clean/uncontended state, isolated diagnostics proved the orchestrator's own real latency is genuinely ~13–28 seconds per tool-using turn; under contention, some individual turns observed during this session took many minutes even though the underlying mechanism was never actually stuck (confirmed directly: process CPU time inspected mid-turn was always eventually accruing, never permanently zero, and the isolated repros always completed once memory pressure cleared). This is reported as a real, measured environmental fact, not a code defect — and it is why the originally-planned reduced-scale suite (21 dev conversations + a 15-turn long-context conversation + 10 cancellation cycles) was itself further trimmed mid-session (to 12 dev conversations + 6 long-context turns + 4 cancellation cycles, with results now logged incrementally rather than only in one final dump, so genuine progress is never lost to a later interruption) and, even at that reduced size, was not fully completed within a single session's reasonable time budget.

**What was actually completed, run once, and manually read in full** (not sampled, not summarized from memory): 11 real conversations / 15 real turns, covering all 9 of Section 38's required categories (feature, howto, capability, roadmap, relationship ×2, paraphrase, false-premise, unknown, multiturn ×2):

- Every one of the 15 turns validated clean on delivery (`validation.ok: true`, zero structural-leak/repetition/narration findings in the final delivered answer) and used zero handles, internal ids, file paths, or tool-call syntax in operator-facing text.
- **Zero `MODEL_CONTRADICTION` events** (Section 48's own decisive test): every capability, roadmap, and relationship claim matched its tool result exactly, including `relationship-1` ("Does Transfer Export happen before Transfer Import?") correctly answering "Yes" with the accurate direction — the exact relationship Stage 2.1's own DEC-024 fixed a backwards canonical edge for, now independently confirmed correct through the full Stage-1-through-4 stack via a real model.
- `unknown-1` ("Does AutoIngest support facial recognition tagging?") is the one turn that needed the regeneration/validator safety net in practice, not merely in mocked tests: its first draft was rejected, the bounded single regeneration ran, and the delivered answer was a clean, correct "No" — real, working evidence of Sections 25–27 under genuine model output, not a simulated failure.
- Real multi-turn continuity (Section 13) confirmed directly: in `multiturn-1`, "Does that change the original files?" correctly resolved "that" to the metadata-repair operation from the immediately-preceding turn, and answered from existing conversational context in ~2.7s with zero new tool calls — a concrete, measured demonstration of the design goal in Section 13's own worked example, not an assumption.
- Single-turn latency (a fresh question, tool calls included): 17.0–27.1s. Same-session follow-up turns needing no new tool calls: 2.7–4.3s. These are the true, uncontended figures; see the environmental note above for why some raw session timestamps during this run were far higher.

This is a genuine, disclosed gap, not fabricated evidence — see the Stage 4 final report for the full accounting.

No blind suite, no freeze, and no stochastic re-run phase was attempted this session, consistent with this harness's own header disclosure from when it was first written.

## Postscript — Stage 4.1 Qualification Continuation (2026-09-07)

Stage 4.1 authorized a qualification-only continuation (explicitly: no redesign unless testing revealed a genuine defect) targeting exactly the gaps the Stage 4 postscript above disclosed as unreached: real long-context behavior, real orchestrator-level cancellation, and the still-open `CONTEXT_LIMIT` closure question first raised inconclusively in DEC-025's own Stage 3.1 postscript. A **RESOURCE_BASELINE** precheck at session start (`top`/`ps`/`vm.swapusage`) confirmed the same severe, disclosed, externally-driven memory-pressure condition as Stage 4 (~34 GiB/36 GiB used, ~825 MiB free, load avg ~2.1, zero lingering Qwen processes) — reported honestly rather than waited out, since this is a background job with no way to force a quieter window.

A new harness, `services/qwenOrchestrator/electronQualificationHarnessStage41.js`, ran once, real-model, real-Electron, end to end without interruption: **19 new dev conversations** (26 turns; not overlapping Stage 4's original 11) spanning feature/howto/capability/roadmap/relationship/paraphrase/false-premise/unknown/retrieval-challenge/multiturn categories, **2 real long-context conversations** (6 turns each, real tool calls, no synthetic content), the mandatory **context-limit closure test** (Section 14), and **6 real orchestrator-level cancellation cases** at varied abort timing (5ms–3000ms after the prompt).

### A genuine defect found, fixed, and re-verified: proactive context-budget guard

The context-limit closure test — built by fetching real Stage-2 knowledge content via `session.knowledgeOps` and injecting it as a ~30,239-estimated-token synthetic history (76 turns) directly via `runtime.setSessionHistory()`, deliberately bypassing this stage's own post-turn `_maybePrune()` — reproduced the exact gap DEC-025's Stage 3.1 postscript left open: the very next `sendMessage()` call surfaced a raw `CONTEXT_LIMIT` from node-llama-cpp's own default context-shift strategy ("did not return a history that fits the context size"), and a follow-up turn on the same session hit the identical error again — the session was left genuinely unusable, not merely slow. Root cause: `_maybePrune()` only ever runs *after* a turn completes; nothing in `sendMessage()` checked the budget *before* prompting, so an already-over-budget history (however it got that way) had no defense before reaching node-llama-cpp's own internal recovery, which is not guaranteed to succeed.

**Fix** (`services/qwenOrchestrator/session.js`): a new `_ensureBudgetBeforeTurn(userText)` method, run at the start of `sendMessage()` before the first `_promptOnce()`, mirrors `_maybePrune()`'s own pruning hierarchy (reusing `pruneHistoryToFit`/`estimateTokens`, no new logic) but runs proactively; plus, as defense-in-depth for the rarer case of a single turn's own combined prompt overflowing mid-request, a reactive one-shot fresh-context reset-and-retry if `CONTEXT_LIMIT` still occurs. Both paths reuse existing, already-qualified machinery — no new model, no per-question patch, no retrieval tuning.

Two new regression tests (`test/qwenOrchestratorSession.test.js`) cover both halves directly: pre-turn pruning demonstrably happens *before* the prompt is sent (call-order assertion, not just call-count), and a simulated `CONTEXT_LIMIT` session-error is recovered with exactly one retry rather than surfaced to the caller. The two pre-existing pruning tests required the fake test child to become state-aware (`setSessionHistory`/`resetSession` now actually update the fake's own history, matching real node-llama-cpp behavior) — both still pass unchanged in outcome. Full suite: 18/18 orchestrator-session tests, 40/40 pure-module tests, 17+18+21 Stage-3/3.1 tests, all green; the only failures in the full 37-file repository regression (5 files) are pre-existing, unrelated `services/logger.js`/`app.getPath` environment issues in metadata/XMP tests, confirmed unchanged by this work.

**Re-verified against the real model** (not only the fake-child unit tests): the identical synthetic-oversized-history injection, repeated after the fix against the real Qwen artifact, now completes cleanly — `_ensureBudgetBeforeTurn` pruned the injected history down to the 2-turn floor before prompting (`freshContextCount: 0`, i.e. the softer prune path sufficed here), the model gave an honest "I don't have enough confirmed AutoIngest information to answer that confidently" rather than hallucinating from the now-discarded context, and a follow-up turn confirmed the session fully usable afterward. `CONTEXT_LIMIT` is now closed at the orchestrator level: budget detection is deterministic and proactive, pruning/fresh-context runs before generation is attempted, raw native overflow does not reach the caller in the tested path, and the session survives.

### Real long-context and real cancellation: both now qualified

Both real 6-turn long-context conversations completed without ever needing a mid-conversation fresh-context reset (`freshContextCount: 0` throughout both; context usage grew smoothly from ~2.7K to ~11.6K tokens against a 21,840-token budget, never approaching it for these particular topic sequences) — the softer pruning steps were never even needed at this conversation length, and the multi-turn continuity check at the end of each conversation ("summarize what we were just discussing") answered correctly both times. This exercises the real code path, not a proof that longer real conversations never reach the harder pruning/reset tiers — see the open finding below.

All 6 real cancellation cases acknowledged within single-digit milliseconds of the abort signal regardless of timing (5ms through 3000ms after the prompt) — confirming Section 28's "reject the promise immediately, let the abandoned background generation finish on its own" design holds under real cancellation, not just the mocked test. Every one of the 6 next-turns after a cancellation succeeded and was usable (session never left in a stuck state); next-turn latency ranged 2.4–14.5s, consistent with real inference variance under the disclosed resource condition, not a cancellation-specific cost. This closes Section 42's previously-unreached gap; DEC-025's own ~13.3s worst-case wait finding (the underlying raw-`infer()` cancellation strategy, reused unchanged here) remains the correct reference point for worst-case abandoned-generation duration — nothing in this qualification pass changed or needed to change that strategy.

### Two genuine, disclosed findings — neither patched

Per the Stage 4.1 brief's own strict fix policy (evidence-gated fixes only; no per-question prompt patches, no retrieval tuning from a single failure), both of the following are reported honestly rather than worked around:

1. **A capability-overclaim / hallucinated elaboration**, not a structural leak or crash: asked "Does AutoIngest support importing directly from a cloud storage account?" (`s41-unknown-2`, a deliberately-authored unsupported-capability probe), the model correctly called `search_autoingest` and `capability_status` on the real, genuinely-`AVAILABLE` "Transfer Import" feature, then added an unsupported elaboration beyond what either tool result actually said: "Transfer Drives can be configured to connect to cloud storage accounts." Nothing in the grounded tool JSON asserts this. This is not a direct contradiction of grounded evidence (the mechanical validator's `checkCapabilityGrounding` only checks that *some* grounding tool was called for a capability-shaped answer, not that every specific sub-claim traces to the tool's actual returned content — exactly the disclosed mechanical-only limitation this project's own validator design has always acknowledged) — it is the model over-extrapolating from a real, correctly-retrieved but topically-adjacent fact. A code fix that deep-verified every sub-claim against tool JSON would itself be exactly the kind of "semantic JS reasoning" the fix policy prohibits; this is reported as an open quality gap, not fixed.
2. **An apparent fallback/regeneration cluster concentrated in one long-context conversation.** Cumulative session diagnostics (`regenerationCount`/`fallbackCount`, tracked for the lifetime of the shared session object across this run) show the dev suite's own 20 conversations contributed 3 regenerations and 1 fallback (directly confirmed via each turn's own `regenerated`/`usedFallback` fields), yet by the end of `long-context-0` the cumulative total had risen to 6 regenerations and 4 fallbacks — and stayed exactly there through `long-context-1` and the context-limit test, meaning `long-context-0` alone contributed roughly 3 more regenerations and 3 more fallbacks across its 6 turns, while `long-context-1` (different topics) contributed zero. Two of `long-context-0`'s six answers ("How does transfer export work?", "How does transfer import work?" — both real, well-documented, correctly-answered-in-detail when asked as *isolated* dev-suite questions, see `s41-howto-2`) were suspiciously short (80 characters, matching the exact length of this system's canonical fallback text), consistent with — though not directly confirmed by, since this harness did not retain per-turn `regenerated`/`usedFallback`/full-text fields for long-context turns, a disclosed instrumentation gap — a fallback event. This suggests the same well-documented topic can produce a materially worse outcome later in an accumulating real conversation than as a fresh single-turn question, which is exactly the kind of risk Section 13's long-context qualification exists to surface. **Not fixed**: no code change was made in response to this finding, both because its precise per-turn attribution is not fully instrumented and because a fix scoped to reproduce-then-patch a single observed conversation would itself violate the fix policy's evidence-gating bar. Recorded here as a real, open, unresolved risk for any future long-context qualification pass, which should log full per-turn text and regenerated/usedFallback fields from the start.

### What remains unreached

The full Stage 4.1 protocol (≥100 combined dev conversations across 9 categories, a freeze with file/model hashes, a ≥100-conversation blind suite authored strictly after freeze, and two 100-run stochastic phases) was not reached this session, for the same disclosed reason as Stage 4: real-model qualification at this volume, under this machine's demonstrated resource condition, is not achievable in a single continuous session without either fabricating results or many hours of further unattended execution. This session prioritized closing the three specific gaps Stage 4 left at zero real-model coverage (context-limit, long-context, cancellation) over chasing raw conversation-count volume, and found one genuine, now-fixed-and-re-verified defect plus two genuine, honestly-disclosed-but-unfixed quality findings in doing so. See the Stage 4.1 final report for the complete accounting and verdict.
