## Context

Stage 1's own audit (approved before Stage 2 implementation began) proposed three architectural pieces for Stage 2: a Workflow record type distinct from Capability, a small curated Intent/concept-synonym layer for retrieval, and richer answer contracts. Building these surfaced three real design decisions with genuine alternatives, plus one regression discovered and fixed during Stage 2's own testing that is itself a decision worth recording (how hint-boosted scores interact with the curated `NOT_SUPPORTED` boundary table).

## Options Considered

**1. Workflow record storage — full Markdown parser/validator family (matching bugs/decisions) vs. structured JSON authored directly vs. Markdown reusing generic section-extraction.**
- A full bespoke Markdown family (its own ID allocator, concurrency-safe locking, etc., matching `recordAllocator.js`'s bug/decision/postmortem machinery) was rejected as disproportionate to Stage 2's scope — that machinery exists for high-volume, concurrently-authored record families; Workflow authoring is deliberate and low-volume.
- Structured JSON authored directly was rejected — Workflow content is fundamentally prose (steps, navigation descriptions, limitations) that benefits from Markdown's readability and this repository's existing review conventions, and JSON invites exactly the kind of un-reviewable data-only PRs the evidence-discipline culture here works against.
- **Chosen: Markdown files under `docs/product/workflows/AI-WF-###_NAME.md`, parsed by a new `parseWorkflowFile` that reuses `lib/markdown.js`'s existing generic `extractSection`/`extractHeaderTable` helpers (the same pattern `parseFeatureFile` already uses) — no new parsing primitives, only a new section-name mapping.** ID allocation is manual/sequential (same pattern used for `AI-FEAT-058`/`AI-RM-011`/`DEC-019` in Stage 1), not routed through `recordAllocator.js`'s concurrency-safe lock (that mechanism solves a problem — concurrent sessions racing on the same ID — that doesn't apply to a single deliberate authoring pass).

**2. Concept/synonym retrieval layer — embeddings vs. a large per-question lookup table vs. a small curated concept-cluster map.**
- Embeddings were rejected per the Stage 2 brief's own explicit instruction and Stage 1's own finding that the eval corpus's failures were scoped, fixable retrieval-precision gaps, not a fundamental inability to match natural language.
- A large per-question lookup table was rejected — it doesn't generalize to real paraphrases and was explicitly named as a failure mode to avoid ("Do NOT create a giant question→answer lookup table").
- **Chosen: a small (~18-cluster) curated map (`lib/intentConcepts.js`) of trigger phrases to alternate "hint" query strings, run through the SAME unchanged `lib/query.js` ranker as additional candidate queries** — paraphrase families converge on the same records without a second ranking implementation.

**3. Hint-boosted score vs. curated boundary precedence.**
- Initial implementation let ANY strong feature match (however produced) override a matched `NOT_SUPPORTED` boundary, exactly as Stage 1 had established. Testing found this reintroduced the precise class of bug PR #5's forensic review caught for raw keyword luck — this time via a concept hint: a "team-collaboration" hint aimed at a legitimate paraphrase family ("several users... simultaneously") also fired for "multiple people log in with different roles" (a genuine, correctly-detected multi-user-roles boundary question) and, because the hint scored strongly against `AI-FEAT-048`, silently overrode the boundary.
- **Chosen: a hint-boosted score may never override a curated boundary — only a score the raw, un-hinted question earns on its own may.** `searchCandidates()` now tracks raw-question-only scores (`rawFeatureMatches`) separately from the full hint-expanded merge, and the boundary-override check in `answerQuestion()` uses the raw-only version exclusively. A hint is a recall aid, not a confidence authority.

## Decision

Workflow records: Markdown under `docs/product/workflows/`, parsed via the existing generic section-extraction pattern, manually ID-allocated. Concept layer: a small, curated, inspectable phrase-to-hint map, still routed entirely through the unchanged shared ranker. Boundary precedence: raw-question strength only, never hint-boosted strength, may override a curated `NOT_SUPPORTED` boundary.

## Consequences

- Workflow authoring remains a deliberate, reviewed, low-volume activity — Stage 2 shipped 8 records covering the highest-value operator paths identified in the Phase 1-3 audit, not exhaustive coverage of the ~50 identified intents (recorded as a knowledge gap in `docs/product/workflows/README.md`, not silently absent).
- The concept layer is a real, ongoing maintenance surface: each cluster's `hints` must be verified against real keyword overlap with their intended target records (two clusters — `import-video`, `transfer-resume` — were found mis-aimed during Stage 2's own testing and corrected or deliberately left unboosted; see `AI-FEAT-058`'s Stage 2 Evolution Journal).
- A byproduct of investigating the boundary-override regression: `lib/searchIndex.js`'s `keywordsFrom()` previously had no stopword filtering (only a length>2 filter), which a short Capability summary rarely exposed but a much richer Workflow record's prose did — a real, separate, confirmed defect (`AI-WF-006` won "How do I switch between Stable and Preview versions?" confidently on the words "how"/"between"/"and" alone) fixed by adding a small curated stopword list, benefiting every future record in this family, not just Workflow.
- The raw-vs-hint distinction adds a second parallel candidate-scoring pass (`bestRawByRecord` alongside `bestByRecord`) inside `searchCandidates()` — a small, bounded cost, not a second ranking implementation (still one call to `lib/query.js`'s `runQuery` per candidate query, just tracked separately for the raw one).

## Reconciliation Note

None recorded — consistent with `scripts/product-docs/README.md`'s existing non-goals (no embeddings, no external AI, no network) and with DEC-019's own architecture, which this extends rather than supersedes.

## Post-Decision Evolution (2026-08-14)

The raw-vs-hint boundary precedence rule described above (§ Decision) was itself found insufficient twice after this decision was accepted, both times through this feature's own adversarial testing discipline, not a later architectural rethink:

- **Phase 20/24**: a strong match earned by the raw question itself (not a hint) could still override a boundary — the rule as written correctly blocked hint-inflated overrides, but a genuinely strong raw match on an unrelated real feature (e.g. "Online Registry" strongly title-matching its own parent feature `AI-FEAT-048`) could still suppress a narrower, correctly-matched boundary about that same feature's documented scope. Testing never found a case where this override was CORRECT (i.e., rescued a stale boundary) — only cases where it produced a false `AVAILABLE` for an explicitly-excluded topic.
- **Fix**: an opt-in `hardOverride: true` flag (`lib/statusResolution.js`), applied first to the five Registry-scope boundaries (Phase 20), then extended to all eleven boundaries including the original six Stage 1 exclusions (Phase 24 adversarial review, then confirmed necessary again during the pre-merge acceptance pass) — a boundary carrying this flag is never overridden by any raw match, however strong, because such a boundary makes a narrower scope claim about a real feature rather than "this doesn't exist," and a strong match on the parent feature is not competing evidence against that narrower claim.

This does not supersede the original Decision — the raw-vs-hint distinction itself remains exactly as decided (a hint may never override a boundary); `hardOverride` is an additional, narrower precedence rule layered on top for boundaries where even a raw match must not override. See [AI-FEAT-058](../features/AI-FEAT-058_AUTOINGEST_KNOWLEDGE_ENGINE_STAGE_1.md)'s Phase 20 and Phase 24 evolution entries, and [AI-MEM-0004](../memory/AI-MEM-0004_KNOWLEDGE_PORTAL_STAGE_2_OPERATOR_KNOWLEDGE_ARCHITECTURE.md) for the full narrative.

## Post-Decision Evolution (2026-08-17) — Hard-override trigger specificity

`hardOverride: true` (above) removed the last safety valve against a boundary firing wrongly — once a boundary's keyword matches, nothing can override it, however strong the competing evidence. Part 3 Phase 3's Knowledge Neighborhood Audit found the cost of that tradeoff concretely: `face-recognition`'s keyword list (`['face', 'facial', 'recognize', 'recognition']`) contained bare single-word, dictionary-common tokens — `recognize` hard-overrode genuinely on-topic, high-scoring evidence (AI-FEAT-039 at score 800-900) at maximum confidence (1.0) on a question about Transfer Import's identity-matching behavior that happened to contain the word "recognize" in an unrelated sense. This was distinct in kind from the five Registry-scope boundaries added at Phase 20, whose keyword lists were already deliberately built from specific multi-word phrases for exactly this reason (see the Phase 20 comment on those entries) — that discipline was never retroactively applied to the original six Stage 1 boundaries when `hardOverride` was extended to them at Phase 24.

**Governing principle, adopted at Phase 3's Decision-Interview Decision 1 and applied here:** any trigger capable of bypassing normal evidence ranking must meet a substantially higher specificity standard than ordinary retrieval keywords. It must be semantically specific, corpus-verified, and must not be activatable by an ordinary, unrelated use of one of its component words.

**Audit and remediation (Part 3 Phase 4.2):** all eleven `KNOWN_BOUNDARIES` were audited against the full 153-question regression corpus (the 119-question V1+V2 corpus plus Part 3 Phase 4.1's new 34-case regression-family corpus) and a set of hand-constructed adversarial probes per boundary, checking every keyword for (a) real corpus/probe collisions and (b) plain-substring false-positive risk (e.g. a bare word matching inside an unrelated larger word). Each boundary was classified safe-as-is / demonstrably risky / uncertain from that evidence — see the Phase 4.2 implementation report for the full per-boundary table. Result: only `face-recognition` was demonstrably risky, and only three of its four keywords (`face`, `recognize`, `recognition`) — each confirmed via a real collision (`face` matches inside "interface"/"surface"/"preface"; `recognize` is the original finding; `recognition` collides with a plausible photographer-credit-metadata question). Those three were replaced with specific phrases (`face recognition`, `facial recognition`, `face recognision` [a known, already-tested misspelling], `face detection`, `recognize faces`, `recognize people`) that preserve exact coverage for every real corpus case this boundary must still fire on. `facial` — same single-word shape, same boundary — was audited with the identical adversarial probing and left **unchanged**: no false-positive collision was found for it despite deliberate effort to find one, and per the governing principle an unconfirmed risk is recorded as evidence (`uncertain`), never speculatively edited. The other ten boundaries were confirmed safe-as-is by the same audit — no blanket rewrite was applied.

Two narrow recall-only additions (not correctness fixes, evaluated and verified separately, per the same Decision) were made to `lib/intentConcepts.js`'s trigger lists: `'two operators'` (team-collaboration cluster — a hint-only addition, never itself a hard override) and `'qmz sorting isn't showing up'` / `'metadata audit isn't showing up'` (registry-activity-scope's boundary-widening cluster, deliberately kept anchored to QMZ/metadata-audit context rather than a bare "isn't showing up in the activity feed" phrase, since Import/Transfer activity legitimately does publish under this same boundary and an unanchored phrase would have incorrectly blocked that legitimate case).

## Post-Decision Evolution (2026-08-17) — Keyword-surface normalization and cross-type score comparability

Part 3 Phase 4.3 (Decision 2) implemented a bounded, local relevance adjustment in `lib/knowledgeEngine.js` (`lib/knowledgeSurfaceNormalization.js`) correcting the structural bias whereby a Feature/Workflow record's own keyword-surface size (how many keywords it indexes) gave it more incidental opportunities to accumulate keyword-overlap points, independent of genuine topical relevance — `lib/query.js` itself remains completely unchanged; this is a re-weighting of its already-computed output, never a second ranker. **Governing principle: searchable-surface size must not itself confer retrieval authority.** The correction is dampen-only (a divisor floored at 1.0 guarantees an adjusted score can never exceed the shared ranker's raw score — proved structurally, not per-case), applies only to the keyword-overlap tier (exact-id/alias/title and title-substring matches are untouched), and is restricted to Feature/Workflow entity types (see below for why). Current empirically-selected operating point: `REF=20` (a small reference constant, not an on/off threshold — dampening is continuous), `damping=0.25` (the smallest strength found, by systematic sweep against real corpus data, that robustly resolves the confirmed Gap C bias case while robustly preserving a verified legitimate-large-record case) — these constants are subordinate to the principle above, not the decision itself; do not re-derive the principle from the constants.

**A second, distinct principle, discovered when the above was validated against the full corpus rather than only the hand-picked evidence set (Part 3 Phase 4.3, escalation E1-B):** a score may only be directly compared across candidate classes when those scores remain on a common calibration basis. Restricting normalization to Feature/Workflow types (Bug/Decision/Postmortem are never normalized, because an early all-type version was found to reintroduce the identical near-tie limitation at a wider scale — see the concrete `BUG-002`/"How do I create a new event?" case in the Phase 4.3 report) created a NEW asymmetry: Feature/Workflow scores became dampened while Governance scores stayed on the original raw scale, and the code that decides whether a Governance record displaces a Feature/Workflow record as primary authority (`governanceIsBestEvidence` in `answerQuestion()`) kept comparing one side's dampened number against the other side's undampened number as if they were still equivalent. This let Governance records become relatively over-favored wherever they were already competitive — concretely breaking the `sync-slot` control (`DEC-003` wrongly displacing `AI-WF-006`) and several other cases (`R23`'s `DEC-019`, `P07a`'s `BUG-011`, `P17a`'s `PM-001`, `R03`'s `DEC-003`).

**Resolution (Approach D, of five investigated — A/B/C/E rejected or deferred for lack of evidence, see the Phase 4.3 Cross-Entity Comparability Decision Report for the full comparison):** the surface-normalized (adjusted) score is used for intra-type relevance ordering — Feature-vs-Feature, Workflow-vs-Workflow, and Feature-vs-Workflow (both sides share the same calibration, so this comparison is legitimate and unchanged). The candidate's original **raw** score is used specifically for the cross-type Governance-authority gate — deciding whether a Bug/Decision/Postmortem displaces the selected Feature/Workflow candidate, and the tie count that gate depends on. This restores the exact pre-Phase-4.3 comparison basis for that one gate, without touching how Governance's own score is computed (it was never adjusted) and without reopening the `REF`/`damping` decision. **Do not replace the raw-score lookup with the adjusted score in this gate merely because the adjusted value looks like the newer or more-processed one** — `lib/knowledgeEngine.js`'s own inline comment at this exact point exists to prevent that regression; this paragraph is the canonical explanation it points back to.

**Residual limitations, deliberately not fixed by either Phase 4.3 pass, recorded as findings for future remediation, not accepted product behavior:** (1) near-identical-surface Feature-vs-Feature or Feature-vs-Workflow near-ties (e.g. `AI-WF-008`/`AI-WF-009` sharing an identical matched-token set, `AI-FEAT-047` winning "how do i make an event") cannot be resolved by any surface-size-based signal, since the competing records' evidence is genuinely indistinguishable by token count and surface size alone — a different relevance signal would be needed; (2) single-token keyword-overlap matches on a large-surface record can dampen below `CONFIDENCE_FLOOR` and report `UNKNOWN` rather than the previous weak/hedged `AVAILABLE` — an honest but real recall loss, not extended a floor-protection because a single token can never reach "strong" quality in the first place, so there was no false-confidence risk to correct; (3) `R29` (`AI-FEAT-049` vs `AI-FEAT-043`) remains unresolved — its winning record has genuinely more absolute token evidence, not merely more surface, which this mechanism cannot and should not try to distinguish; (4) `Gap A`/`R05` (`AI-FEAT-038` winning via a concept-hint-injected exact-alias-tier match) are confirmed to be a different, unrelated mechanism (Phase 4.2/`intentConcepts.js` territory), never in scope for this normalization work at all.

## Post-Decision Evolution (2026-08-17) — Classifier hygiene: purpose/rationale "why" questions no longer misclassify as TROUBLESHOOTING

Part 3 Phase 4.4 (Decision 6, hygiene half) corrected a confirmed label-only defect in `lib/questionClassifier.js`: the `TROUBLESHOOTING` rule's `why (can'?t|won'?t|does(n'?t)?)` alternation matched bare "why does" (the `(n'?t)?` group is optional), so a pure purpose/rationale question like "Why does Transfer Import exist?" classified `TROUBLESHOOTING` despite containing no failure/problem signal. **This is a semantic-classification correctness fix, not a Gap C remediation.** Gap C (`AI-WF-006` outranking `AI-WF-009`/`AI-FEAT-039` on this exact question via keyword-surface size — see the Phase 4.3 entry above and `RF-4.3-001`) was never caused by `TROUBLESHOOTING` outranking `EXPLANATION`: both question types already route through the same `workflowPreferredType` boolean in `answerQuestion()`, so classifying this question `EXPLANATION` instead of `TROUBLESHOOTING` does not change, and was never expected to change, its retrieval result. Verified directly: `matchedCapabilities`, `sources`, `capabilityStatus`, `matchQuality`, and `confidence` for "Why does Transfer Import exist?" and the Gap C flagship compound question are byte-identical before and after this fix; `RF-4.3-001` (the retrieval-side reproduction) remains `known-baseline-failure`, unchanged.

**Fix:** narrowed the `TROUBLESHOOTING` rule's why-prefix alternation from `why (can'?t|won'?t|does(n'?t)?)` to `why (can'?t|won'?t|doesn'?t)` (dropping the bare "does" branch), and broadened `failed` to `fail(s|ed)?` so "why did X fail" — a genuine failure form with no other recognized failure keyword — still classifies correctly. Added one new alternative to the `EXPLANATION` rule: `\bwhy (is|was|does)\b.*\b(exist(s)?|created?|design(ed)?|built|build|architected|structured|reason|rationale|authoritative|source of truth)\b`, so a "why is/was/does" question that names a purpose/rationale word routes to `EXPLANATION` instead of falling through to `UNKNOWN`. `TROUBLESHOOTING` is still evaluated earlier in `RULES`, so a genuine failure-form "why" question is never reached by the new alternative. Verified corpus-wide (all 154 V1+V2+V3 questions): exactly 6 classifications changed, all the "why does Transfer Import exist" family (its two phrasings, appearing once each in `knowledgeTestCorpus.js`/`knowledgeTestCorpusV2.js`'s absence and four times across `knowledgeRegressionCorpusV3.js`), all `TROUBLESHOOTING` → `EXPLANATION`; zero unintended drift elsewhere. `RF-4.4-001` promoted from `known-baseline-failure` to `control` (now correctly asserts `expectedClassification: 'EXPLANATION'` and passes); `RF-4.4-002`/`RF-4.4-003` (genuine failure-form controls) continue to pass unchanged.

## Post-Decision Evolution (2026-08-17) — Phase 4.3 extension: absolute-evidence-first ordering, and an open confidence-safety gap

Part 4 closure's standalone-test reconciliation (four pre-existing unit-test failures inherited through Phase 4.4, none caused by it) traced two of the four to a genuine, previously-undisclosed Phase 4.3 consequence, and forensically separated them into two distinct principles — one now fixed by Product Owner-approved extension, one left deliberately open.

**Principle A — absolute evidence vs. normalization (implemented):** surface-size normalization is a secondary relevance calibration. It must not override a genuinely stronger absolute-evidence signal. Among candidates that are BOTH eligible for Phase 4.3's keyword-overlap-tier normalization (`isEligibleForNormalization` — never inferred from entity type alone; an exact-alias/title-tier match must never be pulled into this comparison, per the archive-locking investigation's own caught-and-fixed sandbox bug where an ineligible `AI-FEAT-038` exact-alias match was nearly miscounted as "zero tokens"), stronger matched-token evidence defines the evidence band; surface normalization only orders candidates within an equal-evidence band. Implemented narrowly in exactly two locations: `searchCandidates()`'s final sort, and the `workflowClearlyBeaten` cross-type-but-same-calibration (Feature-vs-Workflow) comparison — nowhere else, no generalization for symmetry. `REF=20`, `damping=0.25`, `lib/query.js`, `knowledgeSurfaceNormalization.js`'s public API, and `governanceIsBestEvidence`/`rawScoreById` cross-type gating are all untouched.

Root cause this fixes: for "How does archive locking differ from the Online Registry?", `AI-WF-006` (4 matched tokens, the only record whose own text draws the requested distinction) lost to `AI-FEAT-048` (3 tokens, zero occurrences of "lock"/"locking") purely because `AI-WF-006`'s surface (223) is damped more than `AI-FEAT-048`'s (40) — a genuine absolute-evidence-advantage suppression, not the already-accepted near-identical-evidence residual class. Discovered via Part 4's standalone-test reconciliation (tests C and D, both asserting the identical question), invisible to V2's own `R16` entry because it checks only status/quality, never primary identity. Fixed; `RF-4.3-EXT-002` promoted to `control`. Verified zero regression against the full 154-question corpus plus every named preserve-list item (Gap C, sync-slot `RF-4.3-000`, R23, R15, W13, Q18, all Governance-primary controls) — with two additional, unrequested bonus fixes found as a side effect: `RF-4.3-002` (Gap C's own compound-question flagship) and V2's `R06`/`R11`, both of which were silently resolving to an unrelated workflow (`AI-WF-008`, "Recover From an Archive Lock Error") despite their own `knownLimitation` text already documenting `AI-WF-006` as the intended answer.

**Hardened classifier disposition, stated precisely (per Decision 7's own discipline — a mechanical flag is not itself a verdict):** running the real `knowledgeEvalClassification.js` before/after this extension reports `{ IMPROVEMENT: 1, REGRESSION: 0, UNEXPLAINED_CHANGE: 3, UNCHANGED: 31 }` against the V3 corpus — **not zero mechanical `UNEXPLAINED_CHANGE` classifications.** The 3 (`RF-5.2-002`, `RF-5.4-005`, `RF-5.4-007`) were each individually investigated: all are `status: known-baseline-failure`, `targetPhase` 5.x (deferred Part 5 territory, out of this extension's scope), with `meetsTargetExpectation` unchanged `false → false` in every case — only the *specific* wrong-primary shifted (e.g. `AI-FEAT-041`→`AI-FEAT-039`, `AI-WF-008`→`AI-WF-006`) as a direct, expected side effect of the newly-approved ordering guard now applying corpus-wide. None represents a newly-introduced passing→failing control, a newly-fabricated capability claim, or any other newly harmful behavior. The accurate summary is therefore: **zero unexplained HARMFUL regressions after forensic disposition, not zero mechanical `UNEXPLAINED_CHANGE` flags** — the two are not the same claim, and this record deliberately keeps both facts visible rather than collapsing them into the more convenient-sounding one.

**Principle B — confidence safety gap (deliberately NOT solved, OPEN):** adjusted-score deconfliction does not necessarily constitute stronger underlying evidence. A remaining defect exists where an originally ambiguous, equal-absolute-evidence match can become `matchQuality: strong` solely because normalization broke the tie for ordering purposes — the tie was never resolved epistemically, only for display/selection. Reproduction: "Does AutoIngest support drone footage import with GPS flight paths?" — no canonical record documents this; `AI-FEAT-032`/`AI-FEAT-018` are raw-tied at 200 (2 tokens each, a coincidental collision on the generic words "import"/"path"), correctly `weak` at Phase 4.2, wrongly `strong` today because `AI-FEAT-032`'s surface (18) sits at/below `REF` and is left completely undamped while `AI-FEAT-018`'s (27) is damped — an artifact of which side of the reference point each candidate's surface happens to fall on, not a real confidence signal.

**This is classified HIGH-PRIORITY DEFERRED RETRIEVAL-SAFETY DEFECT, explicitly reviewed and left open by Product Owner decision (2026-08-17) — not accepted as correct behavior, not resolved.** A blanket fix (raw-tie-preserves-`weak`-quality) was implemented and empirically tested: it fixes this case but is proven unsafe as a general rule — because raw score is always exactly `100 × matchedTokenCount` for this tier, "raw tie" and "equal-token tie" are the identical, structurally indistinguishable condition in both this bad case and three already-accepted good cases (`Q18`, `R15`, `R23`, all legitimate near-ties among genuinely relevant records, each previously reviewed and deliberately accepted as improvements). Applying the blanket rule reverted all three to their pre-Phase-4.3 hedge and additionally broke 3 previously-clean, zero-defect V2 passes (`P01a`, `R01`, `R08`) into new unexplained failures. No per-record carve-out was used to avoid this, per standing governance policy against per-record special cases in production logic — so the rule was rejected outright rather than special-cased.

`RF-4.3-EXT-001` is the permanent, intentionally-failing regression control for this defect (`expectedMatchQuality: 'weak'`, currently actual `'strong'`) — it must remain open and failing; it must not be weakened, given a `knownLimitation` to mask it, or marked resolved without a new mechanism. **Open architectural question, reserved for a future, separately-authorized Product Owner checkpoint, not to be answered by inferring embeddings/vector search/LLM scoring/per-record exceptions as the default path:** "How should Ask AutoIngest determine that an untied normalized winner has enough topical evidence to justify STRONG AVAILABLE, rather than merely being the least-bad member of an originally ambiguous evidence set?"

## Post-Decision Evolution (2026-08-17) — Part 5 Phase 5.1: relationship visibility plumbing (Decision 4 of 8)

Feature → Decision and Feature → Postmortem citations, already extracted by `lib/authorityTopics.js`'s `buildAuthorityIndex()` (used until now only as `knowledgeEvalDiagnostics.js`'s read-only ground-truth oracle), are wired into the live `answerQuestion()` path for the first time: a Feature-primary answer's `sources` now include its own canonical `relatedDecisions`/`relatedPostmortems`, alongside the pre-existing `relatedBugs` → `sourcesForRecord()`'s `openBugs` citation path (Stage 1/2 territory, left untouched — see `governanceRelationshipsForFeature()`'s own code comment for why the two paths were deliberately NOT consolidated: bugs carry a live open/fixed status concept decisions and postmortems have no equivalent of). Fidelity-audited first (Decision 4's own prerequisite): `authorityIndex`'s `relatedBugs`/`relatedDecisions`/`relatedPostmortems` are byte-identical, across all 58 canonical features, to both `lib/featureIndex.js`'s independent parse of the same Lifecycle Metadata fields and to `knowledgeIndex.js`'s existing `openBugs` id list — zero divergence found, no escalation triggered.

**Visibility, not admission — proven, not asserted:** the new citation logic runs entirely inside `sourcesForRecord()`, strictly after `answerFromRecord()` has already finalized which record is primary and how confidently (`matchQuality`/`confidence`), and it never adds a candidate to `matchedCapabilities`. Verified two ways: (1) corpus-wide — every one of the 119 V1+V2 questions' `matchedCapabilities`/score/quality is byte-identical before and after this change, confirmed by diffing the full hardened baseline; (2) case-specific — `RF-5.1-001`/`RF-5.1-003` pin AI-FEAT-032's confidence to the exact pre-existing value (0.4) even with DEC-009/PM-001 now visible.

**No recursive expansion:** `governanceRelationshipsForFeature()` reads only the resolved primary Feature's own one-hop `relatedDecisions`/`relatedPostmortems` — never a cited Decision's or Postmortem's own further relationships. Proven concretely (`RF-5.1-004`): `DEC-009` itself cites two features (`AI-FEAT-019`, `AI-FEAT-032`) in its own canonical header, but `AI-FEAT-019` never leaks into `AI-FEAT-032`'s answer — the schema itself has no decision-to-decision or decision-to-bug field to recurse into in the first place (governance records only ever cite Feature(s)).

**Workflow-primary — inspected, not implemented:** a Workflow's own canonical header table (`Related capabilities`, `Related roadmap milestone`) has no `Related decisions`/`Related bugs`/`Related postmortems` columns at all — verified directly against the schema, not assumed. A Workflow therefore gets no Feature-inherited Governance relationships in this phase; inferring one from a related Feature's own citations would be exactly the kind of unsupported reverse/inherited relationship Decision 4 explicitly rules out. `explainRelationships()` reports this explicitly (`relationships: []`, with a note explaining why) rather than silently returning nothing.

**Incidental correction found during implementation:** `RF-5.2-001`/`RF-5.4-008` (both "How do I recover from an archive lock error?", `AI-FEAT-045`) had `expectedMaxSources: 3` — `AI-FEAT-045`'s own canonical "Related decisions" field cites `DEC-013` (Lock Clearing Must Be Constrained, directly on-topic), which now legitimately appears as a fourth source. Corrected to `expectedMaxSources: 4`, same reasoning Phase 4.1 already applied once (2→3) for the analogous bug-citation case in this identical entry.

New diagnostic seam: `explainRelationships(question, ctx)` (parallel to Phase 4.3's `explainNormalization()`) — reports canonical source, relationship type, projection source, visibility state, and ranking influence (always `false`, provably) for the resolved primary's relationships; never consulted by `answerQuestion()` itself.

## Post-Decision Evolution (2026-08-17) — Part 5 Phase 5.2: minimum-sufficient multi-record neighborhoods (Decision 3 of 8)

Two changes, deliberately kept separate: (1) a small, narrowly-scoped fix to `findCompanionWorkflow()`'s existing Workflow-selection logic, and (2) a new, purely diagnostic module (`lib/knowledgeNeighborhood.js`) that labels — never re-decides — which of an answer's own `sources[]` entries constitute a materially-admitted neighborhood member versus a merely-visible (Phase 5.1) one. Neither changes `lib/query.js`, `REF`/`damping`, `governanceIsBestEvidence`/`rawScoreById` cross-type gating, or which record wins primary anywhere in the 119-question V1+V2 corpus — verified by diffing primary-record identity for every case against Phase 5.1's committed baseline: zero changes.

**The fix — Workflow selection uses independent retrieval strength, not ID order:** `findCompanionWorkflow()` previously broke ties among multiple real candidate companion Workflows by lowest ID alone.
