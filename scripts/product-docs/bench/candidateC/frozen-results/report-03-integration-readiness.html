01 · Executive Recommendation

GO — but as a scoped evidence-layer change, not a pipeline replacement

The Knowledge Model's real production contribution is narrower and lower-risk than "Candidate C wins" might suggest — and that is good news. Tracing the actual production request lifecycle (Section 4) found that the experimental harness never ran through production's real synthesis path at all: it bypassed the schema-constrained JSON generation, safety validation, and handle-resolution that services/localJudge/synthesisAdapter.js already provides today, in favor of raw chat completion. That means integration is not "replace the pipeline with what won the benchmark" — it is "give the existing, already-hardened pipeline better evidence to work from."

Three findings from tracing the real code, not assumed from the experiment reports, drove this recommendation:

  • Production's conversational orchestrator already exists and is already close to Candidate B. lib/conversationalAsk.js — topic-change detection, clarification decisioning, the "not sure" hedge — is live in main/askAutoIngest.js today. Candidate B's one real orchestration difference (the repeated-ambiguity hedge) and its chat-session-replay harness technique were never merged back. This shrinks the "conversational architecture" integration surface to nearly nothing.
  • Production's model is not yet Gemma-4-E4B-it. services/localJudge/modelManager.js still resolves phi-4-mini-instruct-Q4_K_M. Every A/B/C measurement in both checkpoints ran exclusively on Gemma. The model swap is a real, separate, already-implied-but-unimplemented prerequisite — not something this integration can silently assume is done.
  • Production's synthesis is schema-constrained JSON generation, not free-text chat. promptTemplates.js/synthesisSchema.js/safetyValidation.js already provide handle resolution and ID-leakage protection the experimental harness never exercised. The Knowledge Model's job is to feed better evidence into that existing, safer pipeline — not to become a second pipeline.

Recommendation: GO for a phased integration that (1) promotes the Knowledge Model's schema, records, retrieval, and validation into a production module, (2) adapts evidencePackage.js to source from it when coverage exists, with the existing FACT/ACTION-atom path retained as the always-available fallback, and (3) treats the Gemma model swap as a parallel, explicitly-tracked prerequisite rather than an assumption. Full sequencing in Section 18.

03 · Selected Architecture

What "Knowledge Model wins" actually authorizes

The selected architecture is the existing Ask AutoIngest deterministic pipeline, unchanged, plus the corrected Candidate C Knowledge Model as a new evidence source inside that pipeline's existing synthesis stage. This is deliberately narrower than "adopt Candidate B and Candidate C's harnesses as production" — neither harness is production-shaped code, and neither should become it verbatim (Section 8).

Concretely selected for promotion, refactored into production-appropriate modules rather than kept as experimental directory structure:

  1. The KnowledgeRecord schema and its validation (assertValidRecord)
  2. Dimensional knowledge representation (purpose/operatorWorkflow/preconditions/actions/behavior/recovery/relationships/limitations/technicalDetail)
  3. Source/provenance grounding, with the forensic-verified / registry-reshaped tier distinction
  4. The 20 Tier-1 forensic records (re-reviewed once more before promotion — see Section 9)
  5. The Tier-2 mechanical reshape pipeline, including the authoring-normalization fix
  6. Conceptual retrieval (conceptualRetrieve) as an evidence-shaping function, not a replacement retrieval/ranking system
  7. Question-aware dimension selection (DIMENSIONS_BY_TYPE)
  8. Multi-record relevance/scoping (recordRole/scopedQuestionTypes/filterRecordsByRelevance)
  9. Operator-facing vs. technical-detail separation (the authoring contract, Section 10)
  10. The incremental, hash-manifested Tier-2 build
  11. The static leakage/validation test as a permanent regression guard

Not selected: the harness's own model-invocation technique (raw chat completion via LlamaChatSession/setChatHistory), the flat evidence-block string format, and the mock {answer, capabilityStatus, sourceIds: [], steps: [], warnings: [], refused: false} synthesis result shape — all of these exist only because the harness needed something simpler than production's real schema-constrained pipeline to iterate quickly. Production integration adapts the Knowledge Model to feed into the real pipeline's existing shapes, not the other way around.

08 · Components Not to Promote

Harness-only scaffolding

  • The flat evidence-block string format (conceptualRetrieve's evidenceBlock as literal chat-prompt text). Production needs structured fields feeding promptTemplates.js, not a pre-formatted string.
  • The mock synthesis result shape ({answer, capabilityStatus, sourceIds: [], steps: [], warnings: [], refused: false}). Real synthesis output already has a richer, validated shape (synthesisSchema.js) that must not be bypassed.
  • Raw LlamaChatSession/setChatHistory chat-completion invocation. Production's runtime.infer() contract is a stateless, schema-constrained, per-request call. Bringing chat-session replay into production is a real, separate runtime change (Section 15.2/18), not something to smuggle in via the Knowledge Model integration.
  • The KMEXP_CONV_LIMIT/ARCHEXP_CONV_LIMIT-style env-var harness scaffolding, fixture userData directories, and symlink-based embedding-model setup in the harness entry points — purely test-harness plumbing.
09 · Knowledge Model Ownership / Build Lifecycle

One source of truth per tier, no parallel manual truths

Tier 1 — forensic, hand-authored, source-backed

  • Source of truth: the record file itself, hand-edited by whoever did the forensic source read.
  • Generation process: manual — a directed research pass over actual source/tests for a specific feature. Not automatable, and should not be automated; this is where judgment about what's operator-relevant lives.
  • Provenance requirement: every non-obvious claim cites a real file:line, test name, or doc section (unchanged, schema-enforced).
  • Staleness detection: proposed new mechanism — a lightweight content-hash of each cited source file, stored per provenance entry (extending the existing manifest pattern from the Tier-2 build). A CI check flags a Tier-1 record whose cited file has changed since the hash was recorded, for human re-review — it does not auto-regenerate the record (that would defeat the point of a hand-authored, judgment-backed record).
  • Belongs in git: yes, always — this is hand-authored source, not derived output.

Tier 2 — mechanically generated from the capability registry

  • Source of truth: docs/product/generated/knowledge-index.json (the existing capability registry) — not the generated Tier-2 record file itself.
  • Generation process: reshapeRegistry.js, run as an explicit step in the same lifecycle that already regenerates docs/product/generated/* (this repo already has a documented, controlled docs-generation pipeline per CLAUDE.md/docs/product/05_DOCUMENTATION_WORKFLOW.md conventions — Tier-2 generation slots into that existing step, not a new one).
  • Incremental rebuild: already implemented — a per-capability content-hash manifest (knowledgeBuildManifest.json) skips regenerating a Tier-2 record whose source registry entry hasn't changed.
  • Deleted/renamed capabilities: proposed addition — the build script should detect a manifest entry whose featureId no longer exists in the current registry and remove the corresponding generated record (with a logged warning), rather than leaving an orphaned record silently in place. Not yet implemented in the experimental script; needed before production promotion.
  • Belongs in git: yes, generated output committed like any other build artifact in this repo's existing convention (docs/product/generated/* is already committed) — regenerated and re-committed as part of the same PR/process that updates the registry, never hand-edited.

How a future feature adds knowledge

Default path: a new capability lands in the registry (already how every feature gets documented today) → the next Tier-2 regeneration picks it up automatically with no developer action. A developer or reviewer promotes a capability to Tier-1 only when a real operator-facing gap is found (missing recovery behavior, a wrong technical detail, a symptom worth a scoped companion record) — the same bar the original forensic pass used. This avoids two parallel manually-maintained truths: Tier-2 always reflects the registry; Tier-1 only exists where someone deliberately decided the registry's own text wasn't enough.

10 · Authoring Contract

Formalized, source-code-enforced

Operator-facing dimensions (purpose, operatorWorkflow, actions, behavior, recovery, limitations, relationships) must use AutoIngest/operator language. They must never expose function names, IPC channel strings, internal constants/flags, source-code call sequences, or internal documentation/audit-trail commentary.

technicalDetail may contain implementation facts, provided they are source-backed by a code- or test-typed provenance entry and are only surfaced to the operator when the question is explicitly technical (the existing technical-question gate).

Provenance must remain source-backed for every record, at both tiers, with no exception.

The static leakage test should become a permanent production regression test — yes, by default, no concrete reason found otherwise. It caught 12 real latent defects in mechanically-generated content that neither the frozen benchmark nor the generalization set had yet exercised; it costs milliseconds to run; and it encodes a general rule (regex-detectable implementation-language patterns in specific fields), not any benchmark-specific string. It belongs in the same test directory and CI gate as the other scripts/product-docs/test/*.test.js files, run on every change to any Knowledge Model record.

11 · Multi-Record Contract

recordRole / scopedQuestionTypes / filterRecordsByRelevance() — promote as-is

The experimental API is already production-shaped and needs no semantic change, only relocation. Reviewed against the four future-case requirement:

  • Core workflow + troubleshooting companion: already demonstrated (QMZ) and tested (Section 13).
  • Core workflow + recovery-specific companion: supported today — a scoped record with scopedQuestionTypes including TROUBLESHOOTING/CONNECTIVITY also participates when the recovery gate fires, regardless of declared type (already implemented, not a new case).
  • Core workflow + technical companion: not yet exercised by any real record, but the mechanism generalizes without change — a scoped record tagged for no specific question type but relying purely on the technical-question gate would need one small addition: today filterRecordsByRelevance only special-cases the recovery gate, not the technical gate. Recommended small addition during integration: extend the same recovery-gate special-case pattern to the technical gate, so a scoped record with real technicalDetail can participate purely because the question is technical, even without a matching declared type. A one-line, symmetric change to an already-general function — not a new mechanism.
  • N companion records for one feature, no contamination: the filter is per-record and additive; nothing about it caps at two records or assumes a specific pairing.

No semantic changes recommended beyond the one addition above. File relocation only (bench/knowledgeModel/ → lib/knowledgeModel/), consistent with the rest of the promoted code.

12 · Provenance Model

Unchanged, carried forward as-is

Every record's provenance array ({claim, source, type, confidence}) is promoted unchanged. The schema's build-time validator — which already refuses to load a record with unprovenanced recovery/technicalDetail content — becomes a production build-time gate exactly as it is experimentally: lib/knowledgeModel/index.js throws at require-time on any invalid record, so a bad record cannot ship silently. No new provenance mechanism is needed; the existing one already satisfies "every knowledge claim traces to a real citation."

14 · Frozen Benchmark Regression Strategy

Architectural regression suite, not unit tests

The frozen 19-conversation benchmark and the 14-question generalization set remain exactly what they are — a scored, qualitative, model-in-the-loop acceptance instrument — not converted into fast implementation-specific unit-test assertions. Doing so would defeat their purpose (they test the whole pipeline's real behavior, including model output quality, which no mechanical assertion can substitute for).

Proposed regression discipline going forward: after production integration lands, re-run both frozen sets once against the real production pipeline (not the harness) as a dedicated validation step before the integration PR merges. The accepted baseline — 16 PASS / 2 PARTIAL / 1 FAIL, 84.2% clean-pass, 94.7% acceptable — becomes the floor: any future change that would drop below this baseline requires explicit Product Owner review before merging, exactly as this checkpoint's own instruction states. P4's FAIL and H's PARTIAL are documented, accepted residuals at this baseline, not license to let new failures accumulate alongside them.

15 · Known Remaining Issues — Kept Separate

Three findings, three futures, none touched here

15.1 — Eligibility gate (evaluateSynthesisEligibility / authority-downgraded-unknown)

This gate sits upstream of the Evidence Shaping stage the Knowledge Model plugs into (Section 5's flow table). When it fires, synthesis is never attempted at all — the Knowledge Model is never consulted, no matter how good its coverage of the resolved feature is. This is why P4, and the generalization set's NAS-backup and Transfer-Import-resume cases, remain unanswerable regardless of Knowledge Model integration. This checkpoint creates a separate future-work item: investigate synthesisEligibility.js's specific downgrade conditions, confirmed (across two checkpoints, three independent features) to be the single largest remaining ceiling on Ask AutoIngest's answer quality — larger than any architecture change made so far.

15.2 — Question classifier ("Actually, ..." prefix)

questionClassifier.js's HOW_TO regex requires the message to start with "how do I"/"how to"/etc. — a message like "Actually, how do I sort QMZ photos?" falls through to UNKNOWN. Recommendation: a separate, small production hardening task, not bundled into Knowledge Model integration and not investigated alongside broader conversational-query normalization (that would risk scope creep into the eligibility-gate-adjacent territory this checkpoint must not touch). The fix is narrow and mechanical — strip a small set of known conversational lead-in phrases ("actually,", "wait,", "sorry,") before classification, or add each pattern's own start-anchored variant — and should be scoped, tested, and reviewed on its own.

15.3 — Fallback-path leakage (generalization G06)

Traced precisely: when evidencePackage.js's existing atom extraction (the current production path, not anything Candidate C introduces) selects a FACT atom whose source text includes internal documentation/authoring commentary (e.g. "documented as a separate feature file for lineage/continuity reasons"), that commentary can reach the operator-facing answer. This is a pre-existing production risk, surfaced by the experiment but not created by it, and it affects every Ask AutoIngest answer today, independent of any Knowledge Model coverage. Recommendation: a separate production safety-hardening task — extend evidencePackage.js's existing atom-selection logic (or safetyValidation.js's existing checks) with a general filter for documentation/audit-trail-style phrasing, mirroring the Knowledge Model's own authoring-contract regex but applied to the FACT-atom extraction path, not the Knowledge Model path. Not solved by adding a Knowledge Model record for the specific triggering question — that would fix one symptom of a general, pre-existing production gap while leaving the gap itself open for every other capability the Knowledge Model doesn't yet cover.

18 · Recommended Implementation Sequence

Five steps, each independently reviewable

  1. Promote the Knowledge Model as an inert module. Relocate bench/knowledgeModel/ → lib/knowledgeModel/, add the deleted/renamed-capability detection (Section 9) and the technical-gate symmetry fix (Section 11), promote the test suite. No production request path touches it yet — pure addition, zero behavior change, trivially reviewable and revertible.
  2. Land the Gemma model swap as its own PR, independent of the Knowledge Model. Update modelManager.js/synthesisAdapter.js, re-verify production's existing test suite and a manual smoke pass. This can happen in parallel with step 1.
  3. Wire evidencePackage.js's KM-first/fallback branch, behind a simple boolean feature flag if this codebase's existing patterns support one (mirroring PRODUCTION_DOWNLOAD_SOURCE_APPROVED's own precedent in main/askAutoIngest.js) — allows shipping the code path dark before enabling it.
  4. Re-run the frozen 19 + generalization 14 against the real production pipeline (flag enabled), once, unmodified. Compare against the 84.2%/94.7% baseline. Any shortfall blocks merge pending Product Owner review, per the checkpoint's own acceptance-baseline instruction.
  5. Enable the flag, document the decision (Section 16), open the two separate follow-up items (eligibility gate, classifier hardening) as their own tracked work, not bundled into this integration.
