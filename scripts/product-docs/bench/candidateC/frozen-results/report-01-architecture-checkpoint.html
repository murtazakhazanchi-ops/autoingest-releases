01 · Executive Verdict

The knowledge was never the bottleneck alone — the routing around it is

Candidate C (Knowledge Model architecture) produced the two clearest wins of any candidate so far — a fully-grounded resume/recovery answer and an exact, cited technical answer — and also produced the two worst failures of any candidate so far. Read plainly: Candidate C scores worse than both A and B on the frozen 19-conversation acceptance set, by raw pass count. That is reported as found — this checkpoint was explicit that a worse score must be reported, not patched away, and the first frozen run is the experiment. But the aggregate score understates what actually happened, in both directions.

On conversations where the C8 authority layer routes a question all the way through to synthesis, the Knowledge Model produced answers measurably better than anything Candidate A or B produced anywhere in this checkpoint or the last one — a real, cited resume-after-interruption answer (Transfer Export), a real, cited technical storage-location answer (QMZ), and troubleshooting that correctly distinguishes display-sort from sequence-assignment. These are not marginal wins; they are the exact failure modes Section 6 and Section 7 of this checkpoint predicted a better-normalized knowledge representation should fix, and it fixed them.

On two other conversations, newly-authored Knowledge Model content leaked implementation identifiers into ordinary answers, and a troubleshooting-flavored record for one QMZ symptom out-competed the feature's own core workflow record for an unrelated "how do I" question about the same feature. Both are authoring/normalization defects in this checkpoint's own Knowledge Model, not properties of the architecture in principle, and both are narrow, nameable, and fixable without touching retrieval, the model, or the conversational layer.

And on a third class — the checkpoint's own worked example, "can I resume the export or do I gotta start over," plus its generalization-set siblings — the Knowledge Model was never even consulted. The shared, unmodified C8 eligibility gate (evaluateSynthesisEligibility) refuses to call a model at all for these queries, dispatching a canned, honest-sounding-but-empty hedge sentence instead. This is not a Candidate C regression — Candidate A and B hit the identical sentence, verbatim, on the identical case — but it is the single largest remaining ceiling on all three candidates, and no amount of better knowledge fixes it, because better knowledge is never reached.

Bottom line for the four options in front of you: the knowledge-architecture hypothesis is partially confirmed — source-derived, dimensional knowledge measurably improved answers wherever the model actually got to see it — but the current numbers are not yet a case for integration. The smallest rational next step is fixing two authoring defects and widening one eligibility gate, then re-running this exact frozen suite once, before any larger investment.

02 · Source Comprehension

What was actually read

Before writing a single Knowledge Model record, this checkpoint required a genuine forensic pass over the application, not a search for the 19 benchmark questions. Two sources of evidence were used together, deliberately:

  • The existing capability registry (docs/product/generated/knowledge-index.json, 58 capabilities) — itself already substantially source-grounded, not naive prose: entries cite real files and, in places, real line ranges (e.g. AI-FEAT-001's main/main.js lines 196–198 for its security-model claims). This was read in full to establish what the current documentation pipeline already knows, and specifically audited for the checkpoint's central worked example — Transfer Export resume behavior — which turned out to already be described in prose ("checkpoints its own progress so an interrupted transfer can resume") even though the production Ask AutoIngest path still answers UNKNOWN for it. That single finding shaped the rest of the investigation: the gap was hypothesized to be in retrieval and evidence-shaping, not only in missing source facts, and the forensic pass was designed to test that hypothesis directly rather than assume it.
  • Direct, fresh reads of current source code and tests for the 18 capabilities judged most benchmark-critical, dispatched as four parallel forensic passes (source/import, metadata, transfer/archive, special/platform). Each pass re-read the actual implementation files the registry already cited, plus adjacent files, tests, decisions, and bug records the registry did not always cite, specifically hunting for three things the registry's flat prose tends to bury: recovery/interruption behavior, exact technical storage locations, and the real distinguishing rationale between similarly-named features.

What that pass found

The single most consequential finding: Transfer Export's resume behavior is real, precise, and better than the registry's own prose described it. Direct reads of services/transferExportService.js confirmed an atomic, on-disk, per-batch checkpoint ({transferRoot}/.autoingest-transfer/export-checkpoint.json) with a same-size-skip idempotency rule underneath the "re-does that batch" language — meaning a resumed export does not actually re-copy files that already finished, only the files that were mid-flight. Transfer Import turned out to have its own independent, symmetric checkpoint mechanism, which the task framing going in had flagged as possibly absent; it is not. Backup Update Scanning and Archive Folder Adoption, by contrast, genuinely have no resume concept — one is a stateless read-only diff, the other a single atomic file write — and that absence is now recorded as an established fact, not a gap.

Other significant findings: QMZ's sequencing state lives at <qmzRoot>/qmz-sequences.json, written via the same tmp-then-rename atomic pattern used elsewhere in the app, and stores only sequence metadata ({code, number, letter, type}) — which files belong to a sequence is derived by rescanning the folder tree on demand, never stored. The Import Pipeline has a real three-part crash-recovery mechanism (file-level resume, a rollback-not-complete commit rule, and a startup pass that resets any event stuck "in-progress") that the registry did not document at all. The Telemetry Pipeline's own registry summary claimed a settings-controlled kill switch; the actual code is a hardcoded true literal — a stale claim, corrected. Grouping System state was confirmed to be 100% in-memory and unrecoverable across a crash. Several of these were genuinely new facts beyond what any existing AutoIngest documentation established; none were invented — every claim below carries a file, line range, or test citation.

The remaining 40 of 58 capabilities were not given a fresh forensic re-read this checkpoint (see Section 3's tiering) — a disclosed scope boundary, not a silent gap.

03 · Knowledge Model Architecture

A normalized, dimensional representation — not source-code RAG

The checkpoint was explicit that this must not become repository → arbitrary chunks → embeddings → nearest source-code chunks → LLM. What was built instead is a small, hand-shaped schema (knowledgeModel/schema.js) with one record type, KnowledgeRecord, carrying twelve fields: purpose, operatorWorkflow, preconditions, actions, behavior, recovery, relationships, limitations, status, technicalDetail, aliases, and a mandatory provenance array. A build-time validator (assertValidRecord) rejects any record where recovery or technicalDetail is filled in without a matching provenance citation — a structural guard against exactly the failure mode Section 6 warns about (inferring resume behavior from the mere existence of a checkpoint file elsewhere in the codebase).

One design choice worth calling out: a single featureId can resolve to more than one record — QMZ, for instance, has both a core workflow record and a dedicated troubleshooting record for the "sequence numbers look wrong after sorting" symptom. This is dimensional decomposition working as intended in most cases (Section 9's causal analysis credits it for real wins), and it is also the direct cause of one of the two confirmed regressions in Section 10 — the troubleshooting record's content bled into an unrelated "how do I sort" answer when both records were merged for retrieval. That trade-off is discussed honestly, not hidden, in Sections 9 and 12.

Separating knowledge from presentation

The Knowledge Model never writes prose the model repeats verbatim. Retrieval (knowledgeModel/retrieval/conceptualRetrieve.js) selects a small set of dimensions — never the whole record — based on the operator's actual intent, and hands Gemma structured evidence sections (WHAT IT'S FOR, HOW OPERATORS DO THIS, IF INTERRUPTED / RECOVERY, and so on) to compose into a natural answer itself, exactly as the production evidence-block pattern already does. "What is QMZ?" and "I don't understand what that means" both retrieve the same record; the model is asked to re-explain, not re-fetch, matching Section 5's own worked example — confirmed working in transcript J (Section 8).

05 · Provenance Strategy

Every non-obvious claim traces to a real citation

Each KnowledgeRecord carries a provenance array of {claim, source, type, confidence} entries — type is one of code, test, doc, or registry; confidence is high, medium, or low. This is not decorative: the schema's own build-time validator refuses to load a record whose recovery field is filled in without a provenance entry whose claim text mentions recovery/resume/checkpoint/interrupt language, and likewise for technicalDetail requiring a code or test-typed citation. A record that fails this check throws at require-time, before any question is ever answered — provenance is enforced structurally, not by convention.

The two tiers carry different confidence by design and disclosure, not by omission: forensic-verified records cite exact file:line ranges or test filenames from a fresh read this checkpoint; registry-reshaped records cite the existing registry's own already-established sourceFiles list, one level removed from a fresh re-verification. Both are real source evidence — the difference is disclosed in every record's own extractionTier field and surfaced in the transcript metadata for every Candidate C answer in Section 8, so a reviewer can see, turn by turn, whether an answer drew on freshly-verified or registry-inherited evidence.

06 · Incremental Update Strategy

A real, working build pipeline — not a description of one

Section 9 of the checkpoint asked this to be demonstrated, not only designed. knowledgeModel/build/reshapeRegistry.js is a real, runnable pipeline stage: source repository (via the existing capability registry) → mechanical dimensional reshape → validated Tier-2 records → knowledgeModel/index.js's build-time validation gate → retrieval. It maintains a content-hash manifest (knowledgeBuildManifest.json) keyed per capability; re-running the script after no registry change regenerates 0 of 38 records and reports as much:

[reshapeRegistry] wrote 38 Tier-2 records to records/registryReshaped.generated.js (0 regenerated, 38 unchanged since last build)

The Tier-1 forensic-verified records are not currently auto-regenerated — they are the output of a directed research pass (four parallel forensic agents this checkpoint), which is inherently a judgment-driven, not mechanical, step. The realistic production shape this points toward: Tier-2-style mechanical reshaping can run automatically whenever the capability registry itself regenerates (already an existing, controlled step in this codebase's own documentation lifecycle — see docs/product/generated/); Tier-1-style forensic deepening is a periodic, explicitly-triggered research pass over the highest-traffic or highest-risk features, not a per-commit runtime cost, and never something imposed on an operator at question-answering time. Total measured build cost for this checkpoint's own 66-record model: 57ms wall time for an incremental (no-op) Tier-2 rebuild, 328KB of generated JS across six record files — cheap enough that "explicit regeneration step in CI or on release" (the checkpoint's own suggested lifecycle) is comfortably affordable, and "on every user question" was never on the table.

How do I recover from a stale archive lock error?
Assistant
There are two ways to recover from a stale archive lock: 1. **Use `clearSelfLock`**: This is reachable via IPC archive:clearSelfStaleLock. This method only clears a lock if the recorded device name matches your device's hostname. It will only clear the lock if its last heartbeat is older than the heartbeat interval plus 30 seconds, unless you pass `force:true` after confirming no job is running. 2. **Use `releaseStaleLock`**: This is reachable via IPC archive:releaseStaleLock and is available through the Archive Diagnostics repair UI. This releases any device's stale lock, but it re-reads the lock file before deleting it and will abort if the lock has become active again. Both recovery paths first validate that the lock path is within a configured archive root's `.autoingest/locks/` directory.
